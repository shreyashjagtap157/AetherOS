# RFC-0033: Replay Format

Classification: Normative
Authoritative Source: RFC-0033.md
Requirement-ID: RFC-0033-000
Status: Proposed

**Lifecycle note:** Legacy text; treated as Proposed until evidence-gated acceptance.
**Implements invariants:** I-4 (observable state transitions).
**Depends on:** RFC-0031 (Event Model), RFC-0032 (Trace Span).

---

## 1. Scope

This RFC specifies the *replay format*: the on-disk representation of the event log that enables deterministic replay of platform behaviour for debugging, auditing, and forensic analysis. Replay is built on the event model and trace spans.

---

## 2. Normative Requirements

### 2.1 Replay Log Structure

`RFC-0033.1`: The replay log is a sequence of event records, each prefixed by a 4-byte length field, stored as a linear file in chronological order. New events are appended to the log. The format supports random-access replay by binary search over timestamp.

```c
struct replay_log_record {
    uint32            record_len;        // bytes following this field
    struct platform_event event;         // RFC-0031 event
    // followed by record_len bytes of event payload (event.payload_len already accounts for this)
};
```

`RFC-0033.2`: The replay log file has a header:

```c
struct replay_log_header {
    uint32            magic;             // 0x5245504C ("REPL")
    uint16            format_version;    // 1 for this RFC
    uint32            event_count;        // total events in this log file
    uint64            start_timestamp_ns;
    uint64            end_timestamp_ns;
    uint64            first_event_id;     // global event counter at log start
    uint64            checksum;           // CRC32 of entire header (excluding checksum field)
};
```

### 2.2 Deterministic Replay

`RFC-0033.3`: The replay log MUST support deterministic replay: given a log of events from a session and the initial platform state, replaying the events in order MUST reproduce the final platform state.

`RFC-0033.4`: Non-deterministic inputs (hardware interrupts, timers, async I/O completions) are represented as explicit events in the replay log, not as actual hardware events. A replay MUST substitute explicit synthetic events for actual hardware events. Actual hardware events during replay MUST be suppressed or controlled.

`RFC-0033.5`: The replaer MUST provide a mode where it can replay up to a specific event ID (`replay_to(event_id)`) and then pause. This enables interactive debugging.

### 2.3 Snapshot Integration

`RFC-0033.6`: Periodic state snapshots (periodic checkpoints) MAY be included in the replay log as a special `Checkpoint` event containing a compressed state dump. The checkpoint is used to reduce replay startup time for long sessions.

`RFC-0033.7`: Checkpoints MUST be taken at consistent points (where all transactions have committed and no partial operations are in flight). An inconsistent checkpoint MUST NOT be included in the replay log.

### 2.4 Log Rotation

`RFC-0033.8`: The replay log may rotate when it reaches a declared size threshold. Rotation creates a new log file and emits a `ReplayLogRotated` event per `RFC-0031.57` linking the new log to the old.

## 3. Failure Semantics

| Failure                  | Consequence                                                 |
|--------------------------|-------------------------------------------------------------|
| Checksum mismatch on read | Log file corrupted; reconstruction attempted from replica |
| Replay divergence         | Reported as `ReplayDiverged` per RFC-0031.58             |
| Missing events in replay  | Reported as `ReplayGap` per RFC-0031.59                    |
