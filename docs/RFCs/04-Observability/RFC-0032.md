# RFC-0032: Trace Span

Classification: Normative
Authoritative Source: RFC-0032.md
Requirement-ID: RFC-0032-000
Status: Proposed

**Lifecycle note:** Legacy text; treated as Proposed until evidence-gated acceptance.
**Implements invariants:** I-4 (observable state transitions).
**Depends on:** RFC-0031 (Event Model).

---

## 1. Scope

This RFC specifies *trace spans*: a mechanism for correlating events produced by different components during a single logical operation (e.g., a service call, a transaction, a stream transfer). Trace spans are the observability primitive that enables distributed tracing across the platform.

---

## 2. Normative Requirements

### 2.1 Span Structure

`RFC-0032.1`: A trace span has the following structure:

```c
struct trace_span {
    uint64            span_id;           // locally unique within a trace
    uint64            trace_id;           // globally unique trace identifier
    struct endpoint_id source;           // where the trace starts
    uint64            start_event_id;     // first event in this span
    uint64            end_event_id;       // last event in this span (filled on close)
    uint64            start_timestamp_ns;
    uint64            end_timestamp_ns;
    uint8             span_class;        // 0=REQUEST, 1=RESPONSE, 2=INTERNAL, 3=BACKGROUND
    uint8             outcome;          // 0=UNKNOWN, 1=OK, 2=ERROR, 3=TIMEOUT
    uint32            child_span_count;  // number of child spans
    uint64            parent_span_id;    // 0 if this is a root span
};
```

### 2.2 Span Lifecycle

`RFC-0032.2`: A span is created when a component initiates an operation that crosses a component boundary (e.g., sends a message, opens an object, initiates a stream). The span is closed when the operation completes (response received, object closed, stream finished) or when a failure occurs.

`RFC-0032.3`: Spans form a tree: a parent span may have child spans for sub-operations. Child spans share the same `trace_id` but have distinct `span_id`. The `parent_span_id` of a child span refers to the parent.

`RFC-0032.4`: The `span_class` field has the following values and semantics:
- `REQUEST`: inbound call; span opened on receive, closed on reply.
- `RESPONSE`: outbound call; span opened on send, closed on receive of reply or error.
- `INTERNAL`: within-component operation; opened and closed within same component.
- `BACKGROUND`: async background work; may live indefinitely.

### 2.3 Event Correlation

`RFC-0032.5`: Every event produced during a span's active period (`start_event_id` to `end_event_id`) MUST carry the span's `trace_id` in its `correlation_id` field (`RFC-0031.6`). This links events to traces.

### 2.4 Sampled Spans

`RFC-0032.6`: Not all spans need to be fully recorded. A sampling policy (declared in the component manifest) determines which spans are fully instrumented and which are lightweight (just `span_id`, `trace_id`, `start`, `end`). The sampling policy MUST be declared in the conformance declaration.

`RFC-0032.7`: High-urgency events (`urgency >= 200` per `RFC-0031.7`) MUST always be fully recorded, regardless of sampling policy. A span containing a high-urgency event MUST itself be fully recorded.

### 2.5 Outcome Tracking

`RFC-0032.8`: A span's `outcome` field MUST be set on span close:
- `OK` if the operation completed successfully.
- `ERROR` if the operation failed with a declared error code.
- `TIMEOUT` if the operation timed out.
- `UNKNOWN` if the outcome is undetermined (e.g., span abandoned without explicit close).

---

## 3. Failure Semantics

| Failure                  | Consequence                                                 |
|--------------------------|-------------------------------------------------------------|
| Span not closed          | Span recorded with `outcome=UNKNOWN`; event per RFC-0031.56 |
| Missing correlation      | Events not linked to span; observability gap              |
| Sampling discards urgency >= 200 | Non-conformant per RFC-0032.7        |
