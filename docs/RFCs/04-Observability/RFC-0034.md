# RFC-0034: Audit Log

Classification: Normative
Authoritative Source: RFC-0034.md
Requirement-ID: RFC-0034-000
Status: Proposed

**Lifecycle note:** Legacy text; treated as Proposed until evidence-gated acceptance.
**Implements invariants:** I-4 (observable state transitions), I-10 (explicit failure semantics).
**Depends on:** RFC-0031 (Event Model), RFC-0033 (Replay Format).

---

## 1. Scope

This RFC specifies the *audit log*: the persistent, tamper-evident record of security-relevant events required for accountability, compliance, and forensic analysis. The audit log is a filtered, annotated view of the replay log, specialized for security.

---

## 2. Normative Requirements

### 2.1 Security Event Classes

`RFC-0034.1`: The following event classes from the event taxonomy are security-relevant and MUST be recorded in the audit log:

- `Capability` (0x0200) — all events
- `Security` (0x0700) — all events
- `State` lifecycle transitions (Created→Validated, Active→Cold, Expired→Destroyed, etc.)
- `AuthFailure` events from any class
- `AmbientAuthority` events from any class

### 2.2 Audit Record Structure

`RFC-0034.2`: Audit records are stored as persistent State Architecture objects (`RFC-0015`). The audit log is therefore automatically integrity-verified (`RFC-0017`) and versioned (`RFC-0015.7`). The audit log is not a separate logging system; it is a specialized projection of the event model.

```c
struct audit_record {
    struct object_id        record_id;          // RFC-0015 identity
    struct platform_event    event;              // RFC-0031 event
    struct attribution {
        struct thread_id    acting_thread;
        struct domain_id    acting_domain;
        struct capability_token used_cap;
    } attribution;
    uint8                   severity;             // 0=INFO, 1=WARN, 2=CRITICAL
    uint64                  evidence_ref;       // reference to supporting evidence
    struct signature        auditor_signature;   // optional Ed25519 signature
};
```

### 2.3 Tamper Evidence

`RFC-0034.3`: The audit log MUST be tamper-evident: any deletion, modification, or reordering of audit records MUST be detectable. The platform achieves this through the State Architecture's Merkle integrity (`RFC-0017`): audit records are persistent objects whose content is part of the Merkle DAG. Tampering changes the content, which changes the identity.

`RFC-0034.4`: The platform MAY additionally support an auditor signature: a separate offline signing key that signs each audit record block. This is a Safety-Critical profile requirement.

### 2.4 Retention

`RFC-0034.5`: Audit records MUST be retained for a declared minimum period. The retention period is declared in the conformance declaration. For Safety-Critical profile, the minimum retention is 10 years. For Cloud profile, the minimum retention is 1 year.

### 2.5 Capability Lineage

`RFC-0034.6`: The audit log MUST record the full capability lineage for every capability-related event. When a capability is granted, transferred, or revoked, the audit record MUST include the lineage: which capability derived this one, when, and by whom.

## 3. Failure Semantics

| Failure                  | Consequence                                                 |
|--------------------------|-------------------------------------------------------------|
| Audit log full            | Platform MUST prevent new security events; MUST emit `AuditLogFull` per RFC-0031.60 |
| Tampering detected        | `AuditTamperingDetected` per RFC-0031.61; platform alert   |
| Retention period violated | Non-conformant; conformance violation                       |
