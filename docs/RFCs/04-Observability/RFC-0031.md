# RFC-0031: Event Model

Classification: Normative
Authoritative Source: RFC-0031.md
Requirement-ID: RFC-0031-000
Status: Proposed

**Lifecycle note:** Legacy text; treated as Proposed until evidence-gated acceptance.
**Implements invariants:** I-4 (observable state transitions).
**Depends on:** RFC-0007 (Execution Domain), RFC-0013 (Capability Mediation).

---

## 1. Scope

This RFC specifies the *event model*: the canonical representation of every observable state transition in the platform. Every event in the system — from a thread state change to a capability revocation to a storage provider failure — is emitted, attributed, and recorded through this model.

The event model is the foundation for all other Observability RFCs. Trace spans (`RFC-0032`), replay (`RFC-0033`), audit log (`RFC-0034`), and diagnostic query (`RFC-0035`) all derive from this model.

---

## 2. Normative Requirements

### 2.1 Event Structure

`RFC-0031.1`: Every event has the following fixed structure:

```c
struct platform_event {
    uint64            event_id;         // monotonically increasing per-source
    uint64            event_class;       // category (see event class table)
    uint64            event_type;        // specific type within class
    uint64            timestamp_ns;      // scheduling time (RFC-0012)
    struct thread_id  emitter_thread;    // which thread emitted this
    struct domain_id  emitter_domain;    // which domain emitted this
    uint8             urgency;           // 0=lowest, 255=highest (used by Observability)
    uint8             flags;             // PERSISTENT, CAUSED, CORRELATED
    uint64            causation_id;     // event_id of the event that caused this (if CAUSED flag set)
    uint64            correlation_id;    // for grouping related events from same operation
    uint32            payload_len;       // event-specific payload length
    // followed by payload_len bytes of event-specific data
};
```

### 2.2 Event Classes

`RFC-0031.2`: The following event classes are defined, with representative event types:

| Class          | Class ID | Description                                | Example event types             |
|----------------|----------|--------------------------------------------|---------------------------------|
| Execution      | 0x0100    | Thread, dispatch, scheduling              | ThreadStateChanged, DispatchFailed |
| Capability     | 0x0200    | Capability grant, transfer, revoke        | CapGranted, CapRevoked, CapFault |
| State          | 0x0300    | Object lifecycle, transaction, integrity  | ObjCreated, TxnCommitFailed, IntegrityFault |
| Communication  | 0x0400    | Message, endpoint, routing                 | MsgSent, EpDeregistered, RoutFail |
| Storage        | 0x0500    | Storage provider, tiering                  | ProviderOffline, ObjReconstructed |
| Interrupt      | 0x0600    | Interrupt, timer                           | IrqDelivered, TimerFired, IrqStorm |
| Security       | 0x0700    | Security events                            | AuthFailure, AmbientAuthority, LockOrderViolation |

### 2.3 Event Emission Requirements

`RFC-0031.3`: Every architectural invariant or requirement that declares an event MUST emit it. An implementation MUST NOT declare an event requirement and then fail to emit it. Violations are conformance violations.

`RFC-0031.4`: Events MUST be emitted at the moment the state transition occurs, not buffered and emitted later for non-persistent events. Persistent events (`PERSISTENT` flag) are permitted to be buffered and emitted at the next transaction commit boundary.

### 2.4 Causality

`RFC-0031.5`: When an event is caused by another event, the `CAUSED` flag MUST be set and the `causation_id` MUST reference the causative event's `event_id`. This creates the causal chain required for root-cause analysis and replay (`RFC-0033`).

`RFC-0031.6`: When multiple events are semantically part of the same operation, they share the same `correlation_id`.

### 2.5 Filtering and Sampling

`RFC-0031.7`: The Observability Architecture MAY permit components to declare event filters. Filters MUST be declared in the component manifest (`RFC-0002`). Filtering MUST NOT silently discard events with `urgency >= 200` (security-critical). These events MUST be emitted regardless of filter configuration.

### 2.6 Payload Schemas

`RFC-0031.8`: Every event type has a declared payload schema. Payload schemas are defined in the reference implementation's schema registry. The payload schema MUST be machine-readable and versioned.

`RFC-0031.9`: Implementations MUST support payload schemas for all event types declared in this RFC. Unknown event types (not defined in this RFC) MUST be emitted with zero-length payloads and MUST NOT cause conformance violations.

### 2.7 Event References in Other RFCs

`RFC-0031.10`–`RFC-0031.55`: Throughout this suite, events are referenced by their IDs (e.g., `DomainCreated`, `BootstrapMinimumExecutorLoaded`). Each such reference implies a conformance obligation: the event with that name and type MUST be emitted as specified when the relevant state transition occurs.

## 3. Event Naming

`RFC-0031.56`: Every event type has a canonical name of the form `<ClassName><TypeName>`, e.g., `ThreadStateChanged`, `CapGranted`, `TxnCommitFailed`, `StreamOutOfOrder`. These names appear throughout the RFCs as shorthand for the full event specification.

- `CTS-OBS-EVT-4`: validates RFC-0031.5 — causality chain maintained.
- `CTS-OBS-EVT-5`: validates RFC-0031.7 — urgency >= 200 events not filtered.
- `CTS-OBS-EVT-6`: validates RFC-0031.9 — unknown event types do not cause violations.
