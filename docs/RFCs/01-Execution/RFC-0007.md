# RFC-0007: Execution Domain

**Status:** Active.
**Implements invariants:** I-1, I-2, I-3, I-12, I-13.
**Depends on:** RFC-0013 (Capability Mediation), RFC-0037 (Capability Token Format).

---

## 1. Scope

This RFC specifies two closely related concepts. First, the *execution domain*: the boundary at which capability enforcement is performed and within which references are valid. Second, the *bootstrap protocol*: how initial authority is legitimately constructed at system start, binding the first capability to the hardware root of trust.

This RFC implements I-12 (origin of authority specification) and I-13 (address–authority orthogonality) directly and normatively. No other RFC may implement I-12 or I-13.

---

## 2. Part I — Execution Domain Model

### 2.1 Domain Definition

`RFC-0007.1`: An execution domain is the unit of capability isolation. Every object reference, capability, or address is valid only within the domain that created it or a domain to which it has been explicitly delegated.

`RFC-0007.2`: Domain boundaries are enforced by capability mediation (`RFC-0013`). No cross-domain operation is permitted without a valid capability token authorizing it.

`RFC-0007.3`: Domains are hierarchical: a parent domain may create child domains, but child domains may not escape their parent's visibility unless explicitly granted capability access to the parent.

`RFC-0007.4`: Domains own address spaces. An address is valid only within its creating domain. Address validity across domains requires explicit capability-mediated translation.

### 2.2 Domain Lifecycle

`RFC-0007.5`: A domain is created in the state `Created`. The only valid initial transition is to `Active`. A domain transitions to `Destroyed` when all references to all objects within it are released.

`RFC-0007.6`: Domain creation MUST emit a `DomainCreated` event per `RFC-0031.10`. Domain destruction MUST emit a `DomainDestroyed` event per `RFC-0031.11`.

### 2.3 Domain Hierarchy Rules

`RFC-0007.7`: A parent domain retains authority over its children's lifecycle. Destroying a parent domain MUST either:
- Destroy all children first, or
- Orphan children by transferring parent capability to a designated surrogate (documented in the child's manifest).

`RFC-0007.8`: No child domain may inspect or modify its parent's internal state except through explicitly granted capabilities. This is the address–authority separation in practice.

### 2.4 Domain Identification

`RFC-0007.9`: Each domain has a unique, immutable identifier of fixed byte-width, computed from the domain's content-resolved identity at creation time. This identifier is distinct from any capability token and is used only for observability.

## 3. Part II — Bootstrap Protocol (I-12)

The bootstrap protocol constructs initial authority from the non-arbitrary root of trust to the first operational capability.

### 3.1 Bootstrap Stages

```
Stage I  — Firmware Root of Trust
Stage II — Minimum Executor
Stage III — Capability Root
Stage IV — Composition Root
Stage V  — User Components
```

### 3.2 Stage I — Firmware Root of Trust

`RFC-0007.10`: The platform's root of trust at power-on is the hardware itself. This stage begins with hardware reset and terminates when the Minimum Executor (Stage II) receives control.

`RFC-0007.11`: The root of trust is necessarily non-arbitrary. It is anchored in one of:
- Hardware-attestation identity (TPM, TrustZone, or equivalent)
- User-confirmed boot (physical presence confirmation)
- Hardware-bound key unwrapping

`RFC-0007.12`: The specific mechanism used MUST be declared in the conformance declaration (I-12 compliance requirement). An implementation that does not declare its root-of-trust mechanism is non-conformant.

### 3.3 Stage II — Minimum Executor

`RFC-0007.13`: The Minimum Executor is the first software stage to run with platform authority. It is intentionally minimal: its only responsibilities are:
1. Verify its own integrity against the root-of-trust measurement.
2. Construct the platform's first capability token (the **origin capability**).
3. Bind the origin capability to the hardware identity established in Stage I.
4. Transfer control to the Capability Root (Stage III) with the origin capability.

`RFC-0007.14`: The Minimum Executor MUST NOT grant any capability to any component before Stage III without explicit authorization through the origin capability. Violations are non-conformant.

`RFC-0007.15`: The Minimum Executor MUST emit a `BootstrapMinimumExecutorLoaded` event per `RFC-0031.12`.

### 3.4 Stage III — Capability Root

`RFC-0007.16`: The Capability Root receives the origin capability from the Minimum Executor and constructs the initial capability namespace. It creates the following primitive capabilities:

- A **system capability** representing platform-level authority.
- A **composition capability** delegating component-instantiation authority.
- A **state capability** delegating object-identity authority.

`RFC-0007.17`: The Capability Root MUST create a capability-lineage record per `RFC-0034` documenting the origin of each primitive capability it creates.

`RFC-0007.18`: The Capability Root MUST emit `BootstrapCapabilityRootReady` per `RFC-0031.13` and transition to Stage IV by invoking the Composition Root with the composition capability.

### 3.5 Stage IV — Composition Root

`RFC-0007.19`: The Composition Root (`RFC-0002`) receives the composition capability and instantiates the initial service graph from declared manifests. It uses the capabilities provided in Stage III to perform capability routing (`RFC-0003`) and dependency resolution (`RFC-0004`).

`RFC-0007.20`: The Composition Root MUST emit `BootstrapCompositionRootReady` per `RFC-0031.14` and transition to Stage V by instantiating the first user components.

### 3.6 Stage V — User Components

`RFC-0007.21`: User components receive only the capabilities granted to them through composition. No component in Stage V holds ambient authority. Violations of I-2 at this stage are non-conformant.

`RFC-0007.22`: The complete bootstrap path from Stage I to Stage V MUST be reproducible under the Hardware-attested execution mode of the CTS (`Conformance-Test-Suite-Methodology.md` Section 7.2). Non-reproducible bootstrap paths are non-conformant for I-12.

## 4. Data Structures

### 4.1 Domain Identifier

```c
struct domain_id {
    uint8_t bytes[32];          // BLAKE3-256 of canonical domain representation
};
```

### 4.2 Bootstrap Record

```c
struct bootstrap_record {
    struct domain_id root_domain;
    struct capability_token origin_capability;   // RFC-0037
    struct attestation attestation;             // Stage I hardware measurement
    uint32 bootstrap_version;                    // Protocol version for replay safety
    uint64 timestamp;                             // Monotonic; not wall-clock-dependent
};
```

### 4.3 Capability Root Primitive

```c
struct primitive_capability_set {
    struct capability_token system_capability;
    struct capability_token composition_capability;
    struct capability_token state_capability;
};
```

## 5. Failure Semantics

| Failure                  | Consequence                                                         |
|--------------------------|----------------------------------------------------------------------|
| Stage I integrity mismatch | Boot halted; non-conformant                                          |
| Origin capability construction fails | Boot halted; bootstrap event emitted per RFC-0031.15      |
| Stage III capability lineage gap | Boot halted; non-conformant                                  |
| Composition Root instantiation fails | Bootstrap event per RFC-0031.16; retry or halt      |
| Bootstrap reproducibility failure | Safety-Critical profile non-conformant                       |

## 6. Invariant Maintenance

`RFC-0007.23`: The execution domain model MUST satisfy:
- Domain hierarchy is a DAG (no cycles).
- Domain identifiers are unique and immutable.
- Addresses are valid only within their creating domain.
- Capabilities are required for all cross-domain operations (I-1, I-2, I-3).
- Initial authority derives from Stage I root of trust (I-12).
- Authority and address are separate (I-13).
