# RFC-0009: Address Space

## 1. Scope

This RFC specifies the address-space model: how virtual address spaces are created, managed, and enforced for domains (`RFC-0007`). Address space in this platform is capability-addressed: the right to map or unmap memory is mediated by capability tokens, not by UID or process ID.

This RFC does not specify the hardware MMU format or the physical page table structure, which are hardware-specific. It specifies the architectural envelope within which hardware-specific implementations must operate.

---

## 2. Normative Requirements

### 2.1 Address Space Identity

`RFC-0009.1`: Each domain (`RFC-0007`) has exactly one address space. The address space identifier (ASID) is derived from the domain identifier by a deterministic one-way function. ASIDs are immutable for the lifetime of the domain.

`RFC-0009.2`: Address spaces are disjoint by construction: no two domains share the same ASID, and no address in domain A's address space is directly addressable from domain B unless a capability token explicitly authorizes cross-domain memory access.

### 2.2 Mapping

`RFC-0009.3`: Mapping a physical or persistent memory region into an address space requires a valid `MAP` capability token (`RFC-0037`) for the target region. Without this capability, the mapping operation MUST be rejected.

`RFC-0009.4`: The set of rights granted by a `MAP` capability MAY be a subset of full access. The capability MUST document which of `READ`, `WRITE`, `EXECUTE` are granted. The platform MUST enforce these rights at every memory access.

`RFC-0009.5`: Address space updates (map/unmap) MUST be atomic with respect to concurrent dispatch and execution. The CTS verifies this through concurrent-access tests.

### 2.3 Capability-Mediation Integration

`RFC-0009.6`: Every memory access performed by a dispatched thread is checked against the `MAP` capability covering the accessed address range. The check MUST occur in hardware or in a boundary check that cannot be bypassed by software.

`RFC-0009.7`: Capability-mediated address spaces MUST NOT permit a thread to elevate its own rights. If a thread holds only `READ` on a region, attempts to write MUST be caught and rejected even if the underlying hardware would permit it.

### 2.4 Large Pages and Huge Pages

`RFC-0009.8`: The address space model MUST support at minimum two page-size classes: a base page (4 KiB or the nearest hardware-supported base) and a large page (2 MiB or the nearest hardware-supported large size). Huge pages (1 GiB) are RECOMMENDED.

`RFC-0009.9`: Page-size selection MUST be explicit in the mapping request. The platform MAY promote a mapping to a larger page size automatically only if the runtime page-size decision produces a verifiable runtime improvement and does not change the accessible address range.

### 2.5 NUMA Awareness

`RFC-0009.10`: Address space operations MUST expose the NUMA topology of backing pages. Mappings that cross NUMA node boundaries MUST be declared in the conformance declaration. Implicit NUMA crossing is non-conformant for the HPC profile.

### 2.6 Copy-on-Write Semantics

`RFC-0009.11`: The address space model MAY support copy-on-write (CoW) page semantics as a mapping option. When CoW is declared, writes MUST trigger a page copy that is address-space-private before the write is committed. This is distinct from the State Architecture's CoW, which operates at the object layer.

### 2.7 Unmapping and Deallocation

`RFC-0009.12`: When a region is unmapped, all pending writes MUST be flushed and the mapping MUST be invalidated before the unmap operation returns. A subsequent access to the unmapped address MUST generate a fault that is unrecoverable within the same domain without a fresh mapping.

`RFC-0009.13`: Unmapping MUST emit a `RegionUnmapped` event per `RFC-0031.21`.

### 2.8 Address Space Slices

`RFC-0009.14`: A domain's address space MAY be organized into named slices (sub-ranges with independent capability sets). Slice boundaries MUST be aligned to page boundaries. Cross-slice access requires separate capability tokens.

## 3. Address Space State Machine

```
ASID_CREATED
    │ first mapping
    ▼
ASID_ACTIVE — region mapped and accessible
    │ unmaps to zero regions
    ▼
ASID_EMPTY — no mapped regions
    │ domain lifecycle continues; can remap
    ▼
ASID_DESTROYED — domain destroyed; all resources released
```

`RFC-0009.15`: The `ASID_DESTROYED` state is reachable only from `ASID_EMPTY`. Destroying a domain without unmapping all regions is non-conformant.

## 4. Data Structures

```c
struct asid {
    uint64 bits[8];           // platform-specific; minimum 64-bit identifier
};

struct mapping_rights {
    uint8 read  : 1;
    uint8 write : 1;
    uint8 exec  : 1;
    uint8 cow   : 1;          // copy-on-write semantics requested
    uint8 nocache : 1;        // caching policy
    uint4 reserved;
};

struct mapping_descriptor {
    struct asid           asid;
    uint64                vaddr;
    uint64                size;           // MUST be page-aligned
    struct phys_addr       paddr;          // or storage object reference
    struct mapping_rights  rights;
    uint8                 page_size_class; // 0 = base, 1 = large, 2 = huge
};

struct address_space_slice {
    uint64                base_vaddr;
    uint64                extent;
    struct mapping_rights  slice_rights;
};
```

## 5. Failure Semantics

| Failure                  | Consequence                                               |
|--------------------------|-----------------------------------------------------------|
| Missing MAP capability   | Mapping rejected; capability fault per RFC-0013           |
| Rights violation         | Memory access fault; capability revoked or narrowed        |
| NUMA boundary crossing undeclared | Conformance violation for HPC profile          |
| Unmap with pending writes | Writes flushed before unmap completes                     |
| ASID collision           | Non-conformant; ASIDs must be unique per RFC-0009.1       |
