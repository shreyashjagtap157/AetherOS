# RFC-0013: Capability Mediation

**Status:** Active.
**Implements invariants:** I-1, I-2, I-3, I-13.
**Depends on:** RFC-0007 (Execution Domain), RFC-0037 (Capability Token Format), RFC-0038 (Capability Transfer), RFC-0039 (Capability Revocation).

---

## 1. Scope

This RFC specifies the *capability mediation* subsystem: the boundary hardware and software layer that enforces capability-based access control at every access attempt. Capability mediation is the architectural mechanism that implements I-1 (authority mediation), I-2 (no ambient authority), I-3 (least privilege), and I-13 (address–authority orthogonality).

This RFC does not specify capability token format (`RFC-0037`), capability transfer (`RFC-0038`), or revocation (`RFC-0039`).

---

## 2. Normative Requirements

### 2.1 Mediation Boundary

`RFC-0013.1`: Every access to a resource — memory, I/O, interrupt, filesystem object, network endpoint, or any other addressable entity — MUST be checked against a capability token held by the accessor before the access is permitted.

`RFC-0013.2`: The mediation check MUST occur at the earliest point where the accessor can be identified, which for memory is typically at the MMU boundary, and for other resources is at the relevant device driver or service boundary.

`RFC-0013.3`: The mediation boundary MUST NOT be bypassable by software. Any attempt to disable or circumvent capability checks MUST be caught and treated as a capability fault, regardless of privilege level.

### 2.2 Mediation Check

`RFC-0013.4`: A capability mediation check evaluates:
1. Does the accessor hold a valid capability token for the target resource?
2. Does the capability grant the specific rights required for the attempted operation?
3. Is the capability within its declared lifetime, domain scope, and usage bounds?

`RFC-0013.5`: If all three conditions are satisfied, the access is permitted. If any condition fails, the access is denied and a capability fault is raised.

`RFC-0013.6`: A capability fault MUST emit an event per `RFC-0031.31` with: accessor identity, target resource, missing right, and fault type.

### 2.3 Rights Enforcement

`RFC-0013.7`: Rights are declared at capability grant time and are immutable during the capability's lifetime. No rights may be added, removed, or modified after grant. This is the least-privilege invariant (I-3).

`RFC-0013.8`: A capability token with rights `READ` only MAY NOT be used to perform a write. If an accessor attempts a write with a read-only capability, the mediation boundary MUST reject it even if the underlying hardware MMU would permit the write.

### 2.4 Domain Scope

`RFC-0013.9`: A capability token is valid only within the domain that holds it. A capability token from domain A MUST NOT be usable to access resources in domain B unless domain B explicitly grants a derived capability to domain A. Cross-domain capability use without explicit grant is a capability fault.

### 2.5 Address–Authority Orthogonality (I-13)

`RFC-0013.10`: Capability mediation operates on authority tokens. Address resolution (finding *where* a resource is) is a separate operation from authorization (determining *whether* the accessor may act). The platform MUST maintain these as distinct steps. Conflating them — for example, using address bits as authority bits — is non-conformant per I-13.

`RFC-0013.11`: The platform MAY combine address and capability in a single hardware structure (e.g., capability-addressed memory) only if the two concepts remain logically distinct and independently checkable.

### 2.6 Fault Handling

`RFC-0013.12`: When a capability fault occurs, the platform MUST:
- Deny the access immediately.
- Emit the event per RFC-0013.6.
- Either deliver a fault to the accessor thread or terminate it, as declared in the component manifest.

`RFC-0013.13`: A capability fault MUST NOT cause corruption of any resource other than the denied access. Fault isolation is mandatory.

## 3. Mediation State Machine

```
CHECK_REQUEST(accessor, capability, operation)
    │ validate(capability, operation)
    ▼
CHECK_VALID — capability valid and held
    │ check_rights(capability, operation)
    ▼
CHECK_RIGHTS — rights sufficient
    │ check_domain_scope(capability, accessor.domain)
    ▼
CHECK_DOMAIN — scope valid
    │ check_lifetime(capability)
    ▼
CHECK_LIFETIME — within lifetime
    ▼
PERMIT_ACCESS
    (or any check failing)
    ▼
DENY_ACCESS + fault event
```

`RFC-0013.14`: The full check pipeline above MUST be traversed for every access. Short-circuiting any step without evaluating it is non-conformant.

## 4. Data Structures

```c
enum capability_right {
    CAP_RIGHT_NONE      = 0,
    CAP_RIGHT_READ      = 1 << 0,
    CAP_RIGHT_WRITE     = 1 << 1,
    CAP_RIGHT_EXECUTE   = 1 << 2,
    CAP_RIGHT_MAP       = 1 << 3,    // map into address space
    CAP_RIGHT_TRANSFER  = 1 << 4,    // transfer to another holder
    CAP_RIGHT_REVOKE    = 1 << 5,    // revoke dependent capabilities
};

struct capability_fault_record {
    struct thread_id          accessor;
    struct domain_id          accessor_domain;
    struct capability_token   presented_cap; // opaque; checked internally
    uint64                    target_address; // address attempted
    enum capability_right     missing_right;
    uint32                    fault_code;
    uint64                    timestamp;
    enum fault_disposition    disposition; // FAULT_TERMINATE, FAULT_DELIVER, FAULT_LOG
};
```

## 5. Failure Semantics

| Failure                  | Consequence                                               |
|--------------------------|-----------------------------------------------------------|
| No capability held       | Capability fault; access denied                           |
| Insufficient rights      | Capability fault; access denied                           |
| Domain scope violation   | Capability fault; cross-domain event per RFC-0031.31     |
| Lifetime exceeded        | Capability fault; access denied                           |
| Hardware bypass attempt  | Non-conformant; platform MUST detect and halt              |

## 6. Conformance Tests

- `CTS-CAP-MED-1`: validates RFC-0013.1 — every access mediated.
- `CTS-CAP-MED-2`: validates RFC-0013.4 — three-part check enumerated.
- `CTS-CAP-MED-3`: validates RFC-0013.5 — denied access on any check failure.
- `CTS-CAP-MED-4`: validates RFC-0013.7 — rights immutability.
- `CTS-CAP-MED-5`: validates RFC-0013.9 — domain scope enforcement.
- `CTS-CAP-MED-6`: validates RFC-0013.13 — fault isolation.
- `CTS-CAP-MED-7`: validates RFC-0013.14 — no check short-circuiting.

---

## 7. Verification Expectations

Capability mediation is the primary enforcement point for I-1, I-2, I-3, and I-13. It is Tier A by default. The MMU boundary check is hardware-assisted and is Tier A with hardware attestation.
