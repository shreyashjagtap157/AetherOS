# RFC-0011: Scheduler (Layers 1 and 2)

Classification: Normative
Authoritative Source: RFC-0011.md
Requirement-ID: RFC-0011-000
Status: Proposed

**Lifecycle note:** Legacy text; treated as Proposed until evidence-gated acceptance.
**Implements invariants:** I-10 (failure semantics).
**Depends on:** RFC-0008 (Dispatch), RFC-0007 (Execution Domain), RFC-0031 (Event Model).

---

## 1. Scope

This RFC specifies the three-layer scheduler model defined in the Platform Architecture Specification Section 8. It specifies Layer 1 (deterministic core) and Layer 2 (advisory tuning). Layer 3 (offline learning) is outside the scope of this RFC.

The scheduler is responsible for deciding *which thread runs next*, *on which execution unit*, and *for how long*. It operates within the dispatch subsystem (`RFC-0008`) and is invoked at each scheduler decision point.

---

## 2. Scheduler Architecture

### 2.1 Three-Layer Model Overview

| Layer | Role                    | Makes scheduling decisions? | Real-time? | Verification Tier |
|-------|-------------------------|------------------------------|------------|-------------------|
| Layer 1 | Deterministic core      | Yes (guaranteed)             | Yes        | A                 |
| Layer 2 | Advisory tuning        | No — only tunes parameters    | N/A        | B                 |
| Layer 3 | Offline learning       | No — generates recommendations| N/A        | D                 |

`RFC-0011.1`: No scheduling decision in the hot path may involve Layer 2 or Layer 3. The hot path is defined as the code path executed at every scheduler invocation. Layer 2 tuning and Layer 3 recommendations are advisory only and MUST NOT be consulted for any decision that affects timing of any thread in real time.

### 2.2 Scheduler Decision Points

A scheduling decision is triggered at:
- Thread exit or termination
- Thread blocking on a synchronization primitive (`RFC-0028`)
- Thread yielding
- Preemption timeout expiration
- Interrupt-driven migration request
- Layer 2 parameter update

## 3. Part I — Layer 1: Deterministic Core

### 3.1 Algorithmic Class

`RFC-0011.2`: Layer 1 MUST implement a scheduling algorithm belonging to one of the following documented classes:
- **EEVDF** (Earliest Eligible Virtual Deadline First)
- **EDF** (Earliest Deadline First), with explicit admissibility证明
- **PEDLF** (Priority Earliest Deadline First), with explicit priority handling
- Or an equivalent formally documented class with provable bounded latency

`RFC-0011.3`: The chosen algorithm class and its invariants MUST be documented in the conformance declaration, including the formal proof of bounded decision latency.

### 3.2 Thread State Model

`RFC-0011.4`: Every thread managed by Layer 1 occupies exactly one of the following states:

| State       | Description                                                |
|-------------|------------------------------------------------------------|
| `READY`     | Waiting for dispatch; eligible for selection               |
| `RUNNING`   | Currently executing on an execution unit                   |
| `BLOCKED`   | Waiting for a synchronization primitive or I/O             |
| `YIELDED`   | Voluntarily relinquished timeslot; eligible when requeued  |
| `PREEMPTED` | Involuntarily descheduled before quantum expiry            |
| `EXITED`    | Terminated; resources being reclaimed                      |

`RFC-0011.5`: State transitions MUST emit events per `RFC-0031.24` with the thread ID, old state, new state, and reason code.

### 3.3 Real-Time Guarantees

`RFC-0011.6`: Layer 1 MUST provide a documented worst-case dispatch latency from decision point to thread execution. This bound MUST be declared in the conformance declaration and verifiable by CTS.

`RFC-0011.7`: Layer 1 MUST guarantee that for any set of N periodic threads with individual execution budgets Ei and periods Pi, where Σ(Ei/Pi) ≤ U (with U the proven utilization bound of the implemented algorithm class), all deadlines are met.

`RFC-0011.8`: Layer 1 MUST support at minimum 256 distinct priority levels, unless the hardware provides fewer, in which case the hardware maximum is the limit.

### 3.4 Scheduling Decision

`RFC-0011.9`: The scheduling decision algorithm for a given set of READY threads on a given execution unit MUST be deterministic: given identical thread states and identical scheduling parameters, the decision MUST always select the same thread. Non-determinism in Layer 1 is non-conformant.

`RFC-0011.10`: The scheduling decision MUST NOT consider: Layer 2 tunable parameters, thread identity beyond declared priority/deadline, or any ambient state outside the explicit READY queue state.

### 3.5 Quantum

`RFC-0011.11`: Each dispatch is assigned a time quantum. The quantum size MUST be configurable per execution unit and MAY be adjusted by Layer 2 (RFC-0011.17). Default quantum is platform-defined.

`RFC-0011.12`: A thread that exhausts its quantum without blocking or yielding transitions to PREEMPTED and is re-queued to the READY state with a new deadline (for EDF-class) or priority (for priority-class).

## 4. Part II — Layer 2: Advisory Tuning

### 4.1 Role

`RFC-0011.13`: Layer 2 observes system behaviour and adjusts Layer 1 scheduling parameters without making scheduling decisions. Layer 2 has no authority to select a thread, select an execution unit, or determine quantum expiry.

`RFC-0011.14`: Layer 2 operates asynchronously from the scheduling hot path. Layer 2 runs at a lower priority than any RUNNING thread and MUST NOT preempt any thread to perform its tuning computation.

### 4.2 Observable Inputs

`RFC-0011.15`: Layer 2 observes:
- CPU utilization per execution unit (per-core and NUMA node)
- Memory pressure indicators
- I/O wait proportions
- Per-thread blocking latency histories
- Interrupt load
- Power consumption

These are read-only observations; Layer 2 produces no writes to scheduling state.

### 4.3 Tunable Parameters

`RFC-0011.16`: Layer 2 MAY tune the following parameters:
- Per-thread quantum size
- Per-NUMA-node scheduling weight
- Load-balancing thresholds between execution units
- I/O-bound thread boost parameters
- Preemption aggressiveness (within declared bounds)

`RFC-0011.17`: All parameter changes MUST be documented with a version number and timestamp. Parameter changes MUST emit events per `RFC-0031.25`. Layer 2's parameter set MUST be readable by the CTS for verification.

### 4.4 Prohibited Actions

`RFC-0011.18`: Layer 2 MUST NOT:
- Select which thread runs next
- Directly assign a thread to a specific execution unit
- Modify a thread's deadline or priority directly
- Override Layer 1's dispatch decision
- Make any decision affecting real-time thread guarantees

Violations of these prohibitions are non-conformant.

### 4.5 Tuning Policy Documentation

`RFC-0011.19`: The tuning policy used by Layer 2 (e.g., proportional-integral-derivative feedback, machine-learned policy) MUST be declared in the conformance declaration. A black-box policy that cannot be described is non-conformant.

## 5. Data Structures

```c
// Layer 1: Thread descriptor
struct sched_thread {
    struct thread_id              tid;
    uint8                         state;         // enum thread_state
    uint64                        deadline;      // for EDF-class schedulers
    uint8                         priority;      // 0–255, 255 = highest
    uint64                        quantum_remaining;
    uint64                        quantum_total;
    struct execution_unit_id      last_unit;     // for load balancing
    uint64                        virt_start_time; // for EEVDF lag accounting
};

struct scheduling_parameter {
    uint64    quantum_ns;                 // Layer 1 quantum in nanoseconds
    uint8     layer2_enabled;             // 0 = Layer 1 only
    uint8     layer2_policy;              // declared policy identifier
    uint16    load_balance_threshold;    // per-unit load difference trigger
};
```

## 6. Failure Semantics

| Failure                          | Consequence                                                       |
|----------------------------------|-------------------------------------------------------------------|
| Layer 1 non-determinism detected  | Non-conformant; CTS must detect and flag                           |
| Deadline miss (real-time thread) | Event per RFC-0031.26; if thread declares hard real-time, failure is conformance violation |
| Layer 1 latency bound exceeded   | CTS fixture; non-conformant                                        |
| Layer 2 makes scheduling decision | Non-conformant                                                    |
| Layer 2 prohibited action        | Non-conformant                                                    |
| Quantum misconfiguration         | Event per RFC-0031.27                                             |

- `CTS-SCHED-4`: validates RFC-0011.9 — determinism (repeated identical inputs → identical output).

- `CTS-SCHED-6`: validates RFC-0011.19 — Layer 2 policy declared.

## 8. Verification Expectations

Layer 1 is Tier A. The scheduling decision algorithm and its invariants are machine-verified or have a machine-checkable proof. Layer 2 is Tier B.
