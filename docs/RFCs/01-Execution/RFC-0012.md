# RFC-0012: Time

**Status:** Active.
**Implements invariants:** I-10.
**Depends on:** RFC-0011 (Scheduler), RFC-0008 (Dispatch).

---

## 1. Scope

This RFC specifies the time model: how time is measured, distributed, and accounted for within the platform. Time is foundational to scheduler correctness (`RFC-0011`), interrupt latency measurement (`RFC-0010`), and distributed execution (deferred to v2).

This RFC does not specify calendar time, wall-clock time, or real-world time synchronization. It specifies the platform's internal time model.

---

## 2. Normative Requirements

### 2.1 Time Sources

`RFC-0012.1`: The platform MUST provide at least two independently disciplinable time sources:

- **Monotonic raw** — a hardware counter that increments monotonically without jumps. Used for measuring durations.
- **Scheduling time** — a time source used for quantum and deadline accounting, which MUST be paused when the execution unit is in an idle or suspended state.

`RFC-0012.2`: Additional time sources (wall-clock, high-resolution performance counters) MAY be provided as separate primitives with declared provenance.

### 2.2 Time Resolution

`RFC-0012.3`: All time sources MUST have a declared tick resolution of at most 1 nanosecond. Implementations on hardware with coarser resolution MUST document the actual resolution and justify its adequacy for the Safety-Critical profile in the conformance declaration.

### 2.3 Distributed Time (Deferred)

`RFC-0012.4`: v1 implementations MUST declare in their conformance declaration whether they support synchronized time across multiple execution domains. Implementations without explicit multi-domain time synchronization MUST NOT claim cross-domain temporal ordering guarantees. Multi-domain time is a v2 feature.

### 2.4 Timer Facilities

`RFC-0012.5`: The platform MUST provide a timer facility with the following operations:
- **One-shot timer** — fires exactly once at or after a specified deadline.
- **Periodic timer** — fires at a regular interval with a declared jitter bound.
- **Timer cancellation** — cancel a pending timer before it fires.

`RFC-0012.6`: Timer fires MUST be delivered as interrupts (`RFC-0010`). The interrupt routing for timer fires MUST be explicitly configured in the routing table.

### 2.5 Deadline Accounting

`RFC-0012.7`: For threads using EDF scheduling (`RFC-0011.2`), the platform MUST provide a per-thread deadline register that increments with the scheduling clock. The deadline register MUST be accessible to the scheduler and MUST emit an event when a deadline is missed.

`RFC-0012.8`: Deadline miss detection MUST emit a `DeadlineMissed` event per `RFC-0031.28`. The event MUST identify the thread and the degree of miss.

### 2.6 Monotonicity

`RFC-0012.9`: The monotonic raw time source MUST NOT go backward. If hardware or software anomaly causes the counter to decrease, the platform MUST either correct it by jumping forward to the last observed value, or halt and emit a `TimeSourceFault` event. Silent backward jumps are non-conformant.

### 2.7 Suspend/Resume

`RFC-0012.10`: When an execution unit transitions to a lower power state (`RFC-0008` idle), the scheduling time source MAY be suspended. When the unit resumes, the scheduling time source MUST be resumed from the exact point of suspension, not reset. Violations are non-conformant.

## 3. Data Structures

```c
struct timesource_descriptor {
    enum timesource_type {
        MONOTONIC_RAW   = 0,
        SCHEDULING_TIME = 1,
        WALL_CLOCK      = 2,
        PERFORMANCE     = 3,
    } type;
    uint64    resolution_ns;      // MUST be ≤ 1,000,000,000 / 1,000,000,000
    uint64    drift_ppm;          // parts per million; 0 = perfect
    uint8     discipline_source; // which other source disciplines this one
};

struct timer {
    struct timer_id       id;
    uint64                deadline_ns;       // absolute or relative per mode
    uint8                 mode;               // ONE_SHOT, PERIODIC, ...
    uint64                period_ns;          // relevant for PERIODIC
    uint64                jitter_bound_ns;    // declared upper bound on delivery jitter
    struct capability_token handler_cap;       // interrupt handler capability
};
```

---

## 4. Failure Semantics

| Failure                  | Consequence                                             |
|--------------------------|--------------------------------------------------------|
| Timer delivery beyond jitter bound | Event per RFC-0031.29              |
| Deadline miss            | `DeadlineMissed` event per RFC-0031.28                 |
| Monotonic raw going backward | Halt or `TimeSourceFault` event per RFC-0012.9 |
| Timer cancellation failure | Event per RFC-0031.30; timer may still fire        |

## 5. Conformance Tests

- `CTS-TIME-1`: validates RFC-0012.3 — resolution declaration.
- `CTS-TIME-2`: validates RFC-0012.5 — timer facility completeness.
- `CTS-TIME-3`: validates RFC-0012.8 — deadline miss detection and event.
- `CTS-TIME-4`: validates RFC-0012.9 — monotonicity.
- `CTS-TIME-5`: validates RFC-0012.10 — suspend/resume correctness.

## 6. Verification Expectations

Time source management is Tier A. Timer facilities are Tier A for Safety-Critical profile, Tier B otherwise.
