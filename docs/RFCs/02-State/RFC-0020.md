# RFC-0020: POSIX Projection

**Status:** Active.
**Implements invariants:** I-11 (declarable profiles).
**Depends on:** RFC-0015 (Object Identity), RFC-0016 (Transaction Model), RFC-0019 (Storage Provider Interface).

---

## 1. Scope

This RFC specifies the *POSIX projection*: a compatible interface layer that maps traditional POSIX filesystem operations (open, read, write, mkdir, link, etc.) onto the State Architecture's object model. The POSIX projection allows existing software to run without modification while gaining the benefits of the State Architecture's capabilities, transactions, and integrity guarantees.

The POSIX projection is a *projection*, not the underlying model. Its purpose is compatibility; it maps POSIX semantics onto State Architecture primitives.

---

## 2. Normative Requirements

### 2.1 Projection Scope

`RFC-0020.1`: The POSIX projection MUST support the following POSIX operations:
- File: open, close, read, write, lseek, truncate, ftruncate, fsync, stat, lstat, fstat, access, chmod, fchmod, chown, fchown, lchown
- Directory: mkdir, rmdir, opendir, readdir, closedir, rewinddir, telldir, seekdir
- Link: link, unlink, symlink, readlink
- Rename: rename (with POSIX atomic semantics over State Architecture transactions)
- File descriptor: dup, dup2, dup3

`RFC-0020.2`: The following POSIX operations are NOT required by this RFC and SHOULD NOT be implemented without explicit profile declaration:
- mmap (address-space mapping via RFC-0009; separate capability path)
- ioctl (device-specific; out of scope)
- flock (advisory locking; see `RFC-0028` Synchronization)

### 2.2 Object Mapping

`RFC-0020.3`: Every POSIX file or directory is represented as a persistent object (`RFC-0015`) in the State Architecture. The object identity is the content hash of the file or directory structure.

`RFC-0020.4`: POSIX metadata (mode, uid, gid, atime, mtime, ctime) is stored as object metadata in the State Architecture and is part of the object's canonical representation for identity purposes.

`RFC-0020.5`: Directory entries are represented as composite objects whose content is the ordered list of (name, object_id) pairs. The directory object's identity is the Merkle root of this list.

### 2.3 Transactional Mapping

`RFC-0020.6`: Every POSIX write operation that is followed by fsync MUST be committed as a State Architecture transaction (`RFC-0016`) at the fsync call. Write operations without fsync are best-effort (subject to the storage provider's own durability guarantees).

`RFC-0020.7`: The POSIX rename operation MUST be implemented as a two-phase State Architecture transaction: the target directory entry is updated and the source is removed atomically. If the target already exists, it is replaced atomically.

### 2.4 Path Resolution

`RFC-0020.8`: Path resolution is performed against the namespace projection. Path components are resolved using the directory object's child list. The resolved final object identity is used for all subsequent operations.

`RFC-0020.9`: Path resolution MUST validate capability tokens at each path component. A process MAY NOT traverse a directory component unless it holds a capability with `READ` and `EXECUTE` (for directories) rights for that component.

### 2.5 Hard Links and Symlinks

`RFC-0020.10`: Hard links are implemented as multiple namespace entries (names) pointing to the same object identity. The link count is maintained as object metadata. When the link count reaches zero, the object transitions per the Lifecycle FSM (`RFC-0018`).

`RFC-0020.11`: Symlinks are stored as objects of a distinguished type. Symlink resolution is performed by the projection and does not require additional capability checks beyond those for the target path component.

### 2.6 Access Control

`RFC-0020.12`: POSIX permission bits (mode, uid, gid) are a projection of the capability system. The projection maps these to the closest matching capability rights set. A process lacking capability rights to a file MUST receive `EACCES` even if POSIX mode bits would permit access.

`RFC-0020.13`: If a file is accessed through a capability with narrower rights than the POSIX mode would grant, the capability's rights take precedence (capability rights are the ground truth; POSIX mode is a compatibility projection).

---

## 3. Deviations from POSIX

`RFC-0020.14`: The POSIX projection MAY deviate from strict POSIX semantics to improve correctness. Known deviations MUST be documented:
- `O_APPEND` on a file opened by multiple processes is atomic at transaction commit time, not at every write (matches POSIX but enforced through transactions).
- `rename()` of an active file is permitted (POSIX forbids this but the State Architecture permits it with a successful lock per `RFC-0028`).
- `stat()` of an active file always reflects the latest committed state; uncommitted writes are invisible.
