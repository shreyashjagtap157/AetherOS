# RFC-0021: Object Projection

**Status:** Active.
**Implements invariants:** I-9 (replaceable mechanisms).
**Depends on:** RFC-0015 (Object Identity), RFC-0016 (Transaction Model), RFC-0019 (Storage Provider Interface).

---

## 1. Scope

This RFC specifies the *object projection*: a direct interface for applications that want to interact with the State Architecture's object model natively, without the POSIX compatibility layer. The object projection exposes objects as first-class entities with their full lifecycle, integrity, and transactional properties.

---

## 2. Normative Requirements

### 2.1 Object API

`RFC-0021.1`: The object projection MUST provide:
- `object_create(content)` — create and commit a new object; returns `object_id`
- `object_get(id)` — retrieve object content
- `object_update(id, new_content)` — update object (creates new identity); returns new `object_id`
- `object_delete(id)` — initiate lifecycle destruction (`RFC-0018`)
- `object_get_metadata(id)` — retrieve lifecycle state, size, integrity proofs
- `object_list_versions(id)` — return version history (`RFC-0015.7`)

### 2.2 Object Identity

`RFC-0021.2`: Object identity is assigned by the State Architecture at commit time (`RFC-0015`). The object projection does not permit clients to assign or override identities.

`RFC-0021.3`: Object identities are content-resolved. Two objects with identical content get the same identity regardless of creation time. The object projection MUST deduplicate at identity level: `object_create` with identical content to an existing object MUST return the existing identity, not create a duplicate.

### 2.3 Transaction Integration

`RFC-0021.4`: `object_create` and `object_update` are atomic (`RFC-0016`). The returned `object_id` is valid only after commit.

`RFC-0021.5`: The object projection supports batch operations: `object_create_batch(entries[], count)` creates multiple objects in a single transaction. All succeed or all fail.

### 2.4 Version Access

`RFC-0021.6`: `object_get(id)` returns the current version. For historical versions, the projection provides `object_get_at_version(id, version_index)` which retrieves a specific historical identity from the version history.

`RFC-0021.7`: The object projection supports immutable objects (created with an `IMMUTABLE` flag). Immutable objects MUST NOT permit `object_update`. Attempts MUST return an error per `RFC-0031.46`.

## 3. Data Structures

```c
struct object_create_result {
    struct object_id   id;
    uint64             size_bytes;
    uint64             commit_timestamp_ns;
};

struct object_metadata {
    struct object_id          id;
    enum lifecycle_state      state;
    uint64                    size_bytes;
    uint64                    version_count;
    struct signed_integrity  integrity_proof;    // RFC-0017
};

struct batch_create_entry {
    const uint8_t  *content;
    uint64          content_len;
    uint8           flags;          // IMMUTABLE, COMPRESSED, ENCRYPTED
};

struct batch_create_result {
    uint32                    count;
    struct object_create_result results[];
    uint8                     all_succeeded;
};
```

- `CTS-STATE-OBJPROJ-3`: validates RFC-0021.4 — atomic create/update.
- `CTS-STATE-OBJPROJ-4`: validates RFC-0021.5 — batch operations all-or-nothing.
- `CTS-STATE-OBJPROJ-5`: validates RFC-0021.7 — immutable flag enforced.
