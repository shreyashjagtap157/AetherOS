# RFC-0015: Object Identity

Classification: Normative
Authoritative Source: RFC-0015.md
Requirement-ID: RFC-0015-000
Status: Proposed

**Lifecycle note:** Legacy text; treated as Proposed until evidence-gated acceptance.
**Implements invariants:** I-6 (cryptographic integrity), I-13 (address–authority orthogonality).
**Depends on:** RFC-0017 (Integrity Model), RFC-0031 (Event Model).

---

## 1. Scope

This RFC specifies the *object identity model*: how every persistent entity in the platform receives a unique, immutable, content-resolved identifier. Object identity is the foundation on which the State Architecture is built. All persistent state — files, capabilities, VM snapshots, containers, configuration, logs — is represented as an *object* with an *identity*.

Identity does not encode location. Two replicas of the same object share the same identity but live at different locations. The platform manages this distinction.

---

## 2. Normative Requirements

### 2.1 Identity Structure

`RFC-0015.1`: Every persistent object MUST have a single primary identity of fixed byte-width, computed as a content hash of the object's canonical representation.

`RFC-0015.2`: The identity MUST be a cryptographic hash function output with at least 256 bits of output. The hash function used MUST be declared in the conformance declaration. Acceptable functions include BLAKE3-256, SHA-3-256.

`RFC-0015.3`: Two objects with byte-identical canonical representations under identical hash functions MUST produce identical identities. One identity MUST refer to at most one live object at any given moment within a given storage provider.

`RFC-0015.4`: Object identity is immutable. Changing an object's content changes its identity. Old identity becomes a historical reference.

### 2.2 Identity Computation

`RFC-0015.5`: Identity is computed over the *canonical representation* of the object's content. The canonical representation MUST be defined as:
- Content bytes, exactly as stored, with no encoding wrapper
- For composite objects (directories, manifests), over the Merkle structure defined in `RFC-0017` — recursively computing identities of child objects

`RFC-0015.6`: The canonical representation MUST NOT include:
- Metadata (timestamps, owner, ACL) unless the metadata is semantically part of the object's identity claim
- Storage-location information
- Compression encoding if the object is stored compressed

### 2.3 Version History

`RFC-0015.7`: Every object MUST maintain a version history as an immutable sequence of its past identities. Version history is append-only. No version may be removed or reordered.

`RFC-0015.8`: The version history MUST be queryable by an object identity. The query MUST return the sequence of all identities that were ever the object's identity, in chronological order, with commit timestamps.

### 2.4 Replica Differentiation

`RFC-0015.9`: Identity does not distinguish between replicas. Two replicas of the same object at different locations share the same identity. The platform MUST provide a separate replica identifier for location-specific operations.

`RFC-0015.10`: The platform MUST provide a replica-consistency declaration: for a given identity, the implementation MUST declare whether all replicas are guaranteed byte-identical (strong consistency) or eventually consistent (divergence allowed within documented bounds).

### 2.5 Identity and Authority

`RFC-0015.11`: Object identity is independent of capability tokens. A capability token authorizes access to an object; an object identity names it. Conflating identity with capability is a conformance violation per I-13.

`RFC-0015.12`: Capabilities that govern access to an object MAY reference the object by identity. The capability itself holds authority; the identity provides the stable naming anchor.

### 2.6 Self-Healing and Rebalancing

`RFC-0015.13`: When a storage provider detects corruption of an object with a given identity, it MUST attempt to reconstruct the object from an uncorrupted replica (if available) and emit a `ObjectReconstructed` event per `RFC-0031.32`. If no replica is available, it MUST emit `ObjectCorruptionUnrecoverable` per `RFC-0031.33`.

## 3. Data Structures

```c
struct object_id {
    uint8_t bytes[32];         // BLAKE3-256 output
};

struct version_record {
    struct object_id   id;
    uint64             commit_timestamp_ns;   // scheduling time, not wall-clock
    uint8              reason;                // CREATE, UPDATE, RECONSTRUCT
};

struct version_history {
    struct object_id   current_id;
    uint32             version_count;         // number of entries
    struct version_record entries[];          // oldest first
};

struct replica_descriptor {
    struct object_id   object_id;
    uint64             replica_serial;        // per-replica sequence
    struct storage_addr location;             // provider-specific
    uint8              consistency_level;     // 0 = strong, 1 = eventual
};
```

---

## 4. Identity Lifetime

`RFC-0015.14`: An object identity exists from the moment the first version of the object is committed. An identity never expires unless the entire object is explicitly destroyed (`RFC-0018` state `Destroyed`). Destroyed identities MAY be preserved in the version history for audit purposes but MUST NOT be reused for a new object.

---

## 5. Failure Semantics

| Failure                  | Conformation                                                |
|--------------------------|-------------------------------------------------------------|
| Hash collision (genuine) | Identical content at different identities; collision MUST be handled by the storage provider through a documented disambiguation protocol |
| Replica divergence       | Event per RFC-0015.10; eventual-consistency declaration filed |
| Reconstruction failure   | `ObjectCorruptionUnrecoverable` event; object marked failed |
