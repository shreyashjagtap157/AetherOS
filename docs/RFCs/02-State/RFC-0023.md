# RFC-0023: State Conformance

**Status:** Active.
**Implements invariants:** I-4, I-5, I-6, I-9, I-10, I-13.
**Depends on:** RFC-0015 through RFC-0022.

---

## 1. Scope

This RFC collects conformance-test obligations for the State Architecture. It aggregates tests from RFC-0015 (Object Identity), RFC-0016 (Transaction Model), RFC-0017 (Integrity Model), RFC-0018 (Lifecycle FSM), RFC-0019 (Storage Provider Interface), RFC-0020 (POSIX Projection), RFC-0021 (Object Projection), and RFC-0022 (Key-Value Projection), plus state-specific cross-conformance tests.

---

## 2. Normative Requirements

### 2.1 Core Conformance

`RFC-0023.1`: Every implementation MUST pass the following State tests, regardless of profile:

**Object Identity:**
- `CTS-STATE-OBJ-1` through `CTS-STATE-OBJ-6` (RFC-0015)

**Transaction Model:**
- `CTS-STATE-TXN-1` through `CTS-STATE-TXN-6` (RFC-0016)

**Integrity Model:**
- `CTS-STATE-INT-1` through `CTS-STATE-INT-5` (RFC-0017)

**Lifecycle FSM:**
- `CTS-STATE-LC-1` through `CTS-STATE-LC-6` (RFC-0018)

**Storage Provider Interface:**
- `CTS-STATE-PROV-1` through `CTS-STATE-PROV-5` (RFC-0019)

**POSIX Projection:**
- `CTS-STATE-POSIX-1` through `CTS-STATE-POSIX-5` (RFC-0020)

**Object Projection:**
- `CTS-STATE-OBJPROJ-1` through `CTS-STATE-OBJPROJ-5` (RFC-0021)

**Key-Value Projection:**
- `CTS-STATE-KV-1` through `CTS-STATE-KV-5` (RFC-0022)

### 2.2 Cross-State Conformance Tests

`RFC-0023.2`: The following cross-cutting State Architecture tests are mandatory:

- `CTS-STATE-XS-1`: validates that a transaction commit produces a new object identity that is verifiable via the Integrity Model.
- `CTS-STATE-XS-2`: validates that lifecycle transitions occur correctly within transactions — the lifecycle state transitions atomically with the transaction commit.
- `CTS-STATE-XS-3`: validates that removing an optional storage provider does not cause any State invariant to be violated (the removability test, RFC-0019.7).
- `CTS-STATE-XS-4`: validates that object identity and capability are orthogonally handled — a capability can refer to an object by identity without the identity itself being a capability.
- `CTS-STATE-XS-5`: validates that Merkle tree updates are correct under composite object creation (RFC-0017.3).

### 2.3 Profile-Specific Conformance

`RFC-0023.3`: Desktop and Cloud profiles additionally require:
- POSIX projection full conformance (`CTS-STATE-POSIX-*` all pass)

`RFC-0023.4`: Cloud profile additionally requires:
- Cross-provider replication test (`CTS-STATE-PROV-CLOUD-1`)
- Storage provider failover test (`CTS-STATE-PROV-CLOUD-2`)

`RFC-0023.5`: Safety-Critical profile additionally requires:
- Lifecycle FSM correctness proof (`CTS-STATE-LC-SC-1`)
- Transaction recovery test with crash injection (`CTS-STATE-TXN-SC-1`)

### 2.4 Reporting Format

`RFC-0023.6`: State conformance declarations MUST publish:
- Per-RFC test results (pass/fail/skipped with justification)
- Storage providers registered, with provider characteristics
- Object identity hash function declared
- Merkle tree depth configuration
- Lifecycle policy parameters

---

## 3. Conformance Tests

This RFC aggregates tests and declares the following cross-cutting tests:

- `CTS-STATE-CONF-1`: validates RFC-0023.1 — all core tests passed.
- `CTS-STATE-CONF-2`: validates RFC-0023.2 — cross-state tests.
- `CTS-STATE-CONF-3`: validates RFC-0023.3 — Desktop/Cloud profile tests.
- `CTS-STATE-CONF-4`: validates RFC-0023.5 — Safety-Critical profile tests.
- `CTS-STATE-CONF-5`: validates RFC-0023.6 — reporting format.

---

## 4. Verification Expectations

State Architecture conformance is Tier B for aggregation; the underlying components are Tier A.
