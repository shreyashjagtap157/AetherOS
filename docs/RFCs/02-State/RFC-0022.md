# RFC-0022: Key–Value Projection

**Status:** Active.
**Implements invariants:** I-9 (replaceable mechanisms).
**Depends on:** RFC-0015 (Object Identity), RFC-0016 (Transaction Model), RFC-0019 (Storage Provider Interface).

---

## 1. Scope

This RFC specifies the *key–value projection*: a compatible interface for applications that need a key–value store semantics. This projection maps arbitrary byte-string keys to persistent object identities, providing get/put/delete/list with optional transactional grouping.

---

## 2. Normative Requirements

### 2.1 Key–Value API

`RFC-0022.1`: The key–value projection MUST provide:
- `kv_put(key, value)` — store value under key (creates or updates)
- `kv_get(key)` — retrieve value by key
- `kv_delete(key)` — delete key and its associated object
- `kv_exists(key)` — test key existence
- `kv_list(prefix, limit)` — enumerate keys matching prefix
- `kv_txn_open()` — open a key–value transaction
- `kv_txn_put(txn, key, value)` — put within transaction
- `kv_txn_delete(txn, key)` — delete within transaction
- `kv_txn_commit(txn)` — commit transaction atomically (`RFC-0016`)
- `kv_txn_abort(txn)` — abort transaction

### 2.2 Key Encoding

`RFC-0022.2`: Keys are arbitrary byte strings with no maximum length specified by this RFC. The key encoding is opaque to the State Architecture: keys are stored as-is in the key–value namespace object.

`RFC-0022.3`: Key ordering is lexicographic over the byte representation. `kv_list` returns keys in this order.

### 2.3 Value Representation

`RFC-0022.4`: Values are stored as persistent objects (`RFC-0015`). A key maps to an `object_id`. The value's content is the object's bytes. The lifecycle of the key's value follows the Lifecycle FSM (`RFC-0018`).

### 2.4 Transaction Grouping

`RFC-0022.5`: Key–value transactions are implemented as State Architecture transactions. Multiple `kv_put` and `kv_delete` calls within a `kv_txn` are committed atomically.

`RFC-0022.6`: `kv_txn_commit` MUST implement two-phase commit (`RFC-0016`). All keys updated within the transaction either all commit or all abort.

### 2.5 Atomic Compare-and-Swap

`RFC-0022.7`: The key–value projection MUST support `kv_cas(key, old_value, new_value)`: atomically replace the value only if the current value matches `old_value`. This is the primary mechanism for implementing distributed locks using the State Architecture's snapshot isolation.

`RFC-0022.8`: `kv_cas` MUST return a conflict indicator if the current value does not match `old_value`, without modifying state.

## 3. Data Structures

```c
struct kv_pair {
    uint8_t       *key;
    uint64         key_len;
    struct object_id value_id;    // identity of the value object
    uint64         value_len;     // stored for convenience
};

struct kv_transaction {
    struct transaction_id xid;    // RFC-0016 transaction
    struct kv_pair       *pending_writes;
    uint32                 pending_count;
    uint32                 pending_capacity;
};

struct kv_cas_request {
    uint8_t  *key;
    uint64    key_len;
    struct object_id expected_value;     // old value identity
    struct object_id new_value;          // new value identity
};
```
