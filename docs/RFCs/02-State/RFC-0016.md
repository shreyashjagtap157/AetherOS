# RFC-0016: Transaction Model

**Status:** Active.
**Implements invariants:** I-4 (observable state transitions), I-5 (transactional persistence).
**Depends on:** RFC-0015 (Object Identity), RFC-0017 (Integrity Model), RFC-0018 (Lifecycle FSM).

---

## 1. Scope

This RFC specifies the *transaction model*: the mechanism by which persistent state mutations are made atomic, consistent, isolated, and durable. Every persistent mutation in the platform — from a single byte appended to a file to a multi-component configuration change — occurs within a transaction.

This RFC does not specify how transactions are distributed across nodes (v2), nor the specific isolation levels beyond the minimal requirements defined here.

---

## 2. Normative Requirements

### 2.1 Transaction Lifecycle

`RFC-0016.1`: Every transaction occupies exactly one of the following states:

| State       | Description                                                          |
|-------------|----------------------------------------------------------------------|
| `OPEN`      | Transaction initialized; mutations accumulating                      |
| `COMMITTING`| Two-phase commit in progress; mutations finalized                    |
| `COMMITTED` | All mutations durable; visible to subsequent transactions           |
| `ABORTED`   | Transaction rolled back; no mutations applied                        |
| `FAILED`    | Commit failed; recovery in progress                                   |

`RFC-0016.2`: No mutation performed within an OPEN transaction is visible to any other transaction until the originating transaction reaches COMMITTED.

### 2.2 Atomic Commit

`RFC-0016.3`: A transaction MUST be *all-or-nothing*: either all of its mutations are applied, or none are. Partial commits are non-conformant.

`RFC-0016.4`: The platform MUST implement two-phase commit:
- **Phase 1 (Prepare):** All participants validate that they can commit their portion. Participants that can commit enter `PREPARED` state; participants that cannot MUST abort.
- **Phase 2 (Commit):** A coordinator directs all PREPARED participants to finalize. Each participant emits `TransactionPhase2` and enters `COMMITTED`.

`RFC-0016.5`: If Phase 1 fails (any participant cannot prepare), the coordinator MUST direct all PREPARED participants to abort and emit `TransactionAborted` per `RFC-0031.34`.

### 2.3 Durability

`RFC-0016.6`: A transaction is durable when it has reached COMMITTED state and all its mutations are stored in a durable, checksummed form. Durability MUST be verifiable by a client reading the object identity post-commit (`RFC-0015`).

`RFC-0016.7`: Before COMMITTING → COMMITTED transition completes, the platform MUST have persisted the commit record to at least one durable storage provider. Memory-only commit records are non-conformant.

### 2.4 Isolation

`RFC-0016.8`: The platform MUST provide at minimum Snapshot Isolation: transactions observe a consistent snapshot of state as of the transaction's start time, not mutations made by concurrent transactions.

`RFC-0016.9`: Write-write conflicts (two transactions modifying the same object) MUST be detected. The second writer to commit MUST abort with a `WriteWriteConflict` per `RFC-0031.35`. This is the only permitted serializability mechanism for v1.

### 2.5 Nested Transactions

`RFC-0016.10`: The platform MAY support nested transactions: a transaction opened within another transaction. Nested transactions share their parent's isolation snapshot until they independently commit (in which case they merge into the parent) or abort (in which case the parent may decide to continue or abort).

`RFC-0016.11`: Nested transactions that abort MUST NOT automatically abort the parent. Parent abort behavior in response to child abort is a policy decision for the parent component.

### 2.6 Observability

`RFC-0016.12`: Every transaction state transition MUST emit an event per `RFC-0031.36`. Events MUST include the transaction ID, the old state, new state, and participant count.

### 2.7 Recovery

`RFC-0016.13`: After a system crash, all in-progress transactions that were not in COMMITTED state at crash time MUST be recovered as ABORTED. Recovery MUST NOT silently upgrade an ABORTED transaction to COMMITTED.

`RFC-0016.14`: The recovery process MUST emit `TransactionRecovered` events per `RFC-0031.37` for each recovered transaction.

## 3. Two-Phase Commit Protocol

### 3.1 Coordinator Steps

```
1. Coordinator receives COMMIT from client.
2. Coordinator sends PREPARE to all participants.
3. Coordinator waits for all participants to respond PREPARED or ABORT.
4. If any ABORT: send ABORT to all PREPARED participants; state → ABORTED.
5. If all PREPARED: send COMMIT to all participants; state → COMMITTING.
6. Wait for all COMMIT_ACK; state → COMMITTED.
```

### 3.2 Participant Steps

```
1. Participant receives PREPARE.
2. Participant validates local consistency of its mutation.
3. If valid: flush mutation to durable storage (marked pending); respond PREPARED.
4. If invalid: respond ABORT.
5. On receiving COMMIT: mark mutation durable; respond COMMIT_ACK.
6. On receiving ABORT: discard pending mutation; respond ABORT_ACK.
```

### 3.3 Timeout Behavior

`RFC-0016.15`: If the coordinator does not receive a response from a participant within a declared timeout, it MUST abort the transaction and emit `TransactionTimeout` per `RFC-0031.38`. Timeout values MUST be declared in the conformance declaration.

## 4. Data Structures

```c
enum transaction_state {
    OPEN        = 0,
    COMMITTING  = 1,
    COMMITTED   = 2,
    ABORTED     = 3,
    FAILED      = 4,
};

struct transaction_id {
    uint8_t bytes[16];         // RFC-0015 identity of transaction metadata object
};

struct transaction_record {
    struct transaction_id      xid;
    uint64                     start_timestamp_ns;
    uint64                     commit_timestamp_ns;
    enum transaction_state     state;
    uint32                     participant_count;
    struct capability_token    coordinator_cap;
};
```

---

## 5. Failure Semantics

| Failure                  | Consequence                                                    |
|--------------------------|----------------------------------------------------------------|
| Participant Prepare failure | ABORT; event per RFC-0031.34                              |
| Write-write conflict     | Second writer abort; event per RFC-0031.35                     |
| Coordinator crash mid-transaction | Recovery recovers as ABORTED per RFC-0016.13 |
| Participant timeout        | Coordinator aborts transaction; event per RFC-0016.15         |
| Phase 2 partial commit   | Non-conformant; all-or-nothing invariant violated              |
