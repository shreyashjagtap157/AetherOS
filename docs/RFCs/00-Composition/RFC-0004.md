# RFC-0004: Dependency Resolution

Classification: Normative
Authoritative Source: RFC-0004.md
Requirement-ID: RFC-0004-000
Status: Proposed

**Lifecycle note:** Legacy text; treated as Proposed until evidence-gated acceptance.
**Implements invariants:** I-2.
**Depends on:** RFC-0002 (Component Manifest), RFC-0003 (Capability Routing), RFC-0005 (Profile Selection).

---

## 1. Scope

This RFC specifies how a component's declared dependencies are resolved to specific provider versions and instances. Dependency resolution produces the order in which components are instantiated by the Composition Root and the guarantees offered when a dependency cannot be resolved.

This RFC does not specify how individual capabilities are granted (RFC-0003), nor how packages are installed or discovered.

---

## 2. Normative Requirements

### 2.1 Inputs

`RFC-0004.1`: Dependency resolution MUST accept the following inputs:
- The target component manifest.
- All candidate provider manifests indexed by `component-id`.
- The set of profile constraints (`RFC-0005`).
- Any explicit version constraints in the target's `requires` list.

### 2.2 Choice

`RFC-0004.2`: Given a `requires` entry of a target manifest, resolution MUST choose a set of provider manifests satisfying:
- The same `component-id`.
- A version range that overlaps the target's range.
- Compatible profiles.
- Compatible verification tiers, given the target's tier expectations.

`RFC-0004.3`: If multiple providers satisfy the constraint, resolution MUST follow a documented strategy named in the conformance declaration. Acceptable strategies include: highest-version, lowest-version, pinned-via-override.

`RFC-0004.4`: Resolution MUST refuse any provider candidate whose manifest fails to validate (`RFC-0002.19`).

### 2.3 Ordering

`RFC-0004.5`: Resolution MUST order components so that no component is instantiated before its dependencies are instantiated. Cycle detection MUST be performed; cycles MUST be reported per `RFC-0031.4`.

### 2.4 Failure Cases

`RFC-0004.6`: Unsatisfiable dependencies MUST be reported with a reason code indicating: missing provider, version mismatch, profile mismatch, tier mismatch, or cycle.

`RFC-0004.7`: Reports MUST emit events per `RFC-0031.5`.

### 2.5 Update Behaviour

`RFC-0004.8`: When a manifest version is updated, dependency re-resolution MUST be conservative: it MUST NOT alter the instantiated graph unless an explicit update event triggers it.

`RFC-0004.9`: Re-resolution MUST NOT cause silent capability re-grant. Each re-resolution event MUST be exposed through `RFC-0031.6`.

### 2.6 Multi-instance Semantics

`RFC-0004.10`: When a manifest allows multiple instances (`RFC-0002.13`), resolution MUST treat instances as independent post-instantiation; the dependency graph is computed at instantiation but is not redrawn per instance.

---

## 3. Resolution Algorithm

### 3.1 Logical phase ordering

1. Validating all input manifests.
2. Topological ordering, with cycle detection producing `RFC-0031.4` events on detection.
3. Per-dependency matching per Section 2.2.
4. Per-component ordering

### 3.2 Complexity

`RFC-0004.11`: Resolution MUST complete in O(P × D) where P is total candidate provider count and D is total declared dependencies, or better.

---

## 4. Failure Semantics

| Failure                  | Consequence                                                  |
|--------------------------|--------------------------------------------------------------|
| Manifest invalid         | Resolution halted for the affected component                 |
| Cycle detected           | Resolution halted; cycle event emitted                       |
| Unsatisfiable            | Resolution halted; reason-code event emitted                 |
| Override required        | Resolution may proceed with explicit operator override       |
