# RFC-0003: Capability Routing

Classification: Normative
Authoritative Source: RFC-0003.md
Requirement-ID: RFC-0003-000
Status: Proposed

**Lifecycle note:** Legacy text; treated as Proposed until evidence-gated acceptance.
**Implements invariants:** I-1, I-2, I-3.
**Depends on:** RFC-0002 (Component Manifest), RFC-0037 (Capability Token Format), RFC-0026 (Routing).

---

## 1. Scope

This RFC specifies how capabilities declared in a component manifest (`RFC-0002`) are routed, granted, and bound at instantiation time. Cap-routing is the algorithmic counterpart to the Capability Mediation primitives in `RFC-0013`.

This RFC does not specify wire-format routing of capability tokens. That is `RFC-0026`.

---

## 2. Normative Requirements

### 2.1 Declaration

`RFC-0003.1`: A manifest MUST declare per-capability routing intent. Each capability reference MUST include:
- The capability target (`RFC-0037`).
- The narrowing policy applied at grant time.
- The lifetime bounds on the granted capability.

### 2.2 Acquisition

`RFC-0003.2`: Capability acquisition MUST be performed by the Composition Root before instantiation per `RFC-0002.19`.

`RFC-0003.3`: Acquiring a capability to which the requestor has no inference path MUST fail.

### 2.3 Granting

`RFC-0003.4`: Capabilities granted to a component MUST be narrowed versions of capabilities already held by the granting authority. Capabilities MUST NOT obtain rights through grant that the grantor does not itself possess at the moment of grant.

`RFC-0003.5`: A grant MUST produce a new capability token whose rights are documented in the lineage log (`RFC-0034`).

### 2.4 Routing

`RFC-0003.6`: Capability routing decisions MUST be made on the basis of: the requesting component's manifest, the granting component's manifest, the namespace in which the request occurs, and any declared narrowing policy.

`RFC-0003.7`: Two capabilities satisfying the same routing decision MUST NOT depend on ambient context outside the four inputs above.

### 2.5 Revocation

`RFC-0003.8`: Capability grants MAY be revocable or non-revocable. The choice MUST be declared in the manifest's grant section.

`RFC-0003.9`: Revocable grants MUST follow the revocations in `RFC-0039`. Non-revocable grants MAY be revoked through derivative rules.

### 2.6 Failure Cases

`RFC-0003.10`: A capability grant request that fails MUST emit an event per `RFC-0031.3` capturing the failure's reason code and routing inputs.

`RFC-0003.11`: A revocation MUST propagate to the capabilities' dependents as defined in `RFC-0039`.

---

## 3. Routing Algorithm

### 3.1 Inputs

- Component & grantor manifest
- Declared capability target
- Narrowing policy
- Namespace in which the request occurs
- Capability token presented by grantor

### 3.2 Decision

Routing produces one of three outcomes:
1. **Granted** with narrowed capability token.
2. **Denied** with reason code.
3. **Pending** for asynchronous verification; in which case a placeholder capability is granted that the requestor may test against but not consume.

### 3.3 Output

A newly minted capability token (`RFC-0037`) is emitted to the requestor; or, in case 2 or 3, a denied or placeholder record is emitted.

### 3.4 Complexity

`RFC-0003.12`: Capability routing MUST complete in O(log N) or better, where N is the total number of capabilities in the system.

---

## 4. Failure Semantics

| Failure                  | Consequence                                                   |
|--------------------------|---------------------------------------------------------------|
| Manifest invalid         | Routing decision denied with reason code                      |
| Grant not derivable      | Routing decision denied with reason code                      |
| Narrowing failed         | Routing decision denied with reason code                      |
| Routing delayed          | Routing decision pending; placeholder capability emitted      |
| Revocation failed        | Routing decision deferred; see `RFC-0039` for handling        |
