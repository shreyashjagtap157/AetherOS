# RFC-0002: Component Manifest

Classification: Normative
Authoritative Source: RFC-0002.md
Requirement-ID: RFC-0002-000
Status: Proposed

**Lifecycle note:** Legacy text; treated as Proposed until evidence-gated acceptance.
**Implements invariants:** I-2, I-9, I-11.
**Depends on:** RFC-0003 (Capability Routing), RFC-0004 (Dependency Resolution), RFC-0005 (Profile Selection).

---

## 1. Scope

This RFC specifies the format and semantics of the *component manifest*, the declarative document describing a component's identity, dependencies, capabilities, contracts, profile assertions, and lifecycle. The manifest is the input to the Composition Root at bootstrap and is the unit on which the Conformance Test Suite operates.

This RFC does not specify the manifest storage format, signing, or transport. Those are concerns of State Architecture (`RFC-0019`) and Communication Architecture (`RFC-0024`).

---

## 2. Normative Requirements

### 2.1 Identity

`RFC-0002.1`: A manifest MUST contain a single `component-id` field whose value is a content-resolved identifier (`RFC-0015`) computed over the canonical manifest representation.

`RFC-0002.2`: A manifest MUST be self-describing with a `schema-version` field conforming to the manifest schema defined by this RFC at the conformance-test revision supporting it.

`RFC-0002.3`: Two manifests with identical `component-id` MUST be byte-identical under canonical serialization. Divergence implies a non-conformance.

`RFC-0002.4`: A manifest MUST reference its authoring party through a verifiable attestation (`RFC-0034`) field. The attestation MAY be checked by the runtime or out-of-band.

### 2.2 Dependencies

`RFC-0002.5`: A manifest MUST declare all of its dependencies through a `requires` array. Each entry MUST reference another `component-id` plus a version range.

`RFC-0002.6`: A manifest MUST declare any capabilities it grants to dependents through a `provides` array. Each grant MUST specify a capability-validation policy (`RFC-0003`).

`RFC-0002.7`: A manifest MUST declare its declared tier (`RFC-0040`) for every component sub-element where tier is independently testable.

### 2.3 Capabilities and Contracts

`RFC-0002.8`: A manifest MUST declare all capabilities it requires from the system, with rights narrowing declarations. Capabilities inherited transitively through `provides` need not be redeclared.

`RFC-0002.9`: A manifest MUST declare any contract (`RFC-0043`) it satisfies through a `contracts` array, citing the contract identifier.

`RFC-0002.10`: A manifest MUST declare any conformance-test variants it passes, by citing relevant `CTS-TEST-name` IDs.

### 2.4 Lifecycle

`RFC-0002.11`: A manifest MUST declare its lifecycle entrypoint through a `start` field whose value is a relative component-internal address.

`RFC-0002.12`: A manifest MUST declare a graceful shutdown address, possibly identical to `start`, through a `stop` field.

`RFC-0002.13`: A manifest MUST declare the maximum number of concurrent instances permitted (`max-instances`), which MUST be ≥1 and MUST be ≤ the implementation's documented maximum.

### 2.5 Profile and Verification

`RFC-0002.14`: A manifest MUST declare the profiles (`Profiles-Specification.md`) under which it supports operation. A profile claim MUST be supported by the conformance tests cited in Section 2.3.

`RFC-0002.15`: A manifest MUST declare its overall verification tier (`RFC-0040`). A claim that exceeds what the CTS artifacts support is non-conformant.

### 2.6 Update and Rollback

`RFC-0002.16`: A manifest MUST declare its update-strategy (`update-strategy`) atomically replaceable with a prior version. Each update should be a complete manifest; partial-diff updates are non-conformant.

`RFC-0002.17`: A manifest MUST declare its rollback policy through a `rollback-on-failure` boolean. When `true` the runtime MUST be able to revert atomically to a known-good prior version.

### 2.7 Observability

`RFC-0002.18`: A manifest MUST declare which event categories (`RFC-0031`) it explicitly emits. Silently dropping declared events is non-conformant; declaring no events is permitted.

### 2.8 Composition Root Behaviour

`RFC-0002.19`: The Composition Root MUST NOT instantiate a component whose manifest fails to validate per `RFC-0002.1` through `RFC-0002.18`.

`RFC-0002.20`: The Composition Root MUST verify the resolution of every `requires` dependency before instantiation per the dependency-resolution protocol (`RFC-0004`).

## 3. Canonical Representation

The canonical manifest representation SHALL be a deterministic UTF-8 JSON document with:

- Array objects sorted by key
- No insignificant whitespace
- Keys in stable lexicographic order
- Inline-validated against the manifest schema

Manifests are content-addressed by SHA-3-512 of this canonical representation.

---

## 4. Data Structures (reference)

```c
struct component_id {
    uint8_t bytes[64];            // SHA-3-512
};

struct manifest {
    struct component_id id;
    uint32 schema_version;
    struct component_attestation attestation;
    struct dependency requires[];
    struct capability_grant provides[];
    struct contract_ref contracts[];
    struct profile_ref profiles[];
    struct tier_ref tiers[];
    struct component_address start;
    struct component_address stop;
    uint32 max_instances;
    uint8 update_strategy;
    uint8 rollback_on_failure;
    struct event_category events[];
    struct cts_ref tests[];
};
```

`component_id`, `dependency`, `capability_grant`, `contract_ref`, `profile_ref`, `tier_ref`, `event_category`, and `cts_ref` are defined in supporting RFCs cited inline.

## 5. Lifecycle Semantics

### 5.1 Instantiate path

```
1. Composition Root receives a manifest reference.
2. Validate manifest against RFC-0002.1..18.
3. Resolve dependencies per RFC-0004. Failure => abort instantiation.
4. Acquire capabilities per RFC-0003. Failure => abort instantiation.
5. Bind to lifecycle address (start), perform self-test.
6. Emit instantiation event per RFC-0031.1.
7. Re-validate reviews. Instances MAY begin serving.
```

### 5.2 Failure path

A manifest that fails any MUST validation MUST be rejected, and the Composition Root MUST emit a rejection event according to `RFC-0031.2`.

### 5.3 Lifecycle address resolution

Each lifecycle address is a relative path within the component's namespace. Cross-component addresses follow Communication Architecture routing (`RFC-0026`).

---

## 6. Algorithms and Complexity

- Manifest validation: O(N) where N is the number of `requires` entries plus the number of `provides` entries.
- Dependency resolution: O(D × P) where D = number of dependencies, P = number of providers per dependency.
- Capability acquisition: O(K) where K is the number of capabilities declared.

---

## 7. Failure Semantics

| Failure                  | Consequence                                           |
|--------------------------|-------------------------------------------------------|
| Schema invalid           | Manifest rejected, no instantiation                  |
| Verifies-fail            | Manifest rejected, no instantiation                  |
| Dependency unsatisfiable | Manifest rejected, dependency-resolution event emitted |
| Capability unavailable   | Manifest rejected, capability-acquisition event emitted |
| Self-test failure        | Instance aborted, retry policy from runtime applied |

## 8. Conformance Tests

- `CTS-COMP-MAN-1`: validates RFC-0002.1 — content-resolution invariant.
- `CTS-COMP-MAN-2`: validates RFC-0002.5 — dependencies declared.
- `CTS-COMP-MAN-3`: validates RFC-0002.16 — atomic updates.
- `CTS-COMP-MAN-4`: validates RFC-0002.19 — Composition Root rejects invalid manifests.
- `CTS-COMP-MAN-5`: validates RFC-0002.20 — dependency resolution before instantiation.

---

## 9. Verification Expectations

Tier A applies to the Composition Root and the manifest validator. Components that consume manifests are typically Tier C or Tier D.
