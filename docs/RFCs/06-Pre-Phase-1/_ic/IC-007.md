# IC-007: Error Capability (Canonical Error Token)

Implementation Contract ID: IC-007
Source Requirement: RFC-COMPILER-001.25, RFC-COMPILER-001.26, RFC-COMPILER-001.30, RFC-0037.3.1, RFC-0037.4.1, RFC-0037.9.1
Owner: Capability-mediator shim (`aether-cap-model`); generated bindings
Realised Invariants: I-1, I-2, I-10
Implementation Components: ERROR_TOKEN constant; error-code registry; mediator error-token rejection path at CHECK_REQUEST
ABI / Behavioral Contract:
    ERROR_TOKEN (type 11 CAP_ERROR): type = CAP_ERROR; rights = error-code integer (reinterpreted per RFC-0037.4.1); seal = valid HMAC-SHA256 seal computed over first 64 bytes per RFC-0037.9.1; target_object = zeroed struct object_id.
    A CAP_ERROR token is not a resource-access capability: presenting it to the capability-mediator for resource access yields ECAPSTALE at CHECK_REQUEST before rights/domain/lifetime evaluation (RFC-0037.3.1).
    ABI operations return a fixed-width status code separately from any capability result; an error value is data and never authority. Output capability handles are zeroed on failure.
    Error detail follows explicit disclosure policy; it may carry an opaque diagnostic correlation ID but never undelegated resource identity or authority.
CTS Test: CTX-COMP-005
Formal Property: PF-COMP-004 — error token is not a valid capability; error token carries no authority (VT-A)
Observation Record: none
Status: DRAFT
