# RFC-0042: Cohort Update and Rollback Governance

Classification: Normative
Authoritative Source: RFC-0042.md
Requirement-ID: RFC-0042-000
Status: Draft

## 1. Scope

This draft defines the requirements that an implementation contract must refine before profile updates are safe. It is intentionally not accepted and blocks production update claims.

## 2. Candidate requirements

- `RFC-0042.1`: An update unit SHALL be an immutable, content-addressed cohort manifest containing component, interface, schema, firmware, migration, compatibility, and rollback constraints.
- `RFC-0042.2`: Dependency resolution SHALL occur before activation and produce a signed, reproducible plan with no undeclared authority.
- `RFC-0042.3`: Download, verification, staging, activation, health confirmation, commitment, rollback, and failed states SHALL be explicit and crash recoverable.
- `RFC-0042.4`: Boot-critical updates SHALL preserve a separately verified recovery environment and last-known-good cohort.
- `RFC-0042.5`: State migration SHALL declare backward-read, backward-write, rollback, free-space, interruption, and confidentiality behavior. An irreversible migration requires explicit operator authorization and backup evidence.
- `RFC-0042.6`: Activation SHALL be atomic at the declared cohort boundary. Distributed deployments SHALL not imply global atomicity; they use bounded waves, health gates, and compensation.
- `RFC-0042.7`: Signing keys, thresholds, expiration, rotation, revocation, offline roots, emergency policy, transparency evidence, and rollback-attack protection SHALL be specified.
- `RFC-0042.8`: A component may enter the running cohort only with compatible capability rights, ABI/schema contracts, resource budgets, and profile declarations.
- `RFC-0042.9`: Every transition emits an audit commitment and supports deterministic fault injection.
- `RFC-0042.10`: Safety-critical, air-gapped, and fleet profiles define separate approval and recovery policies.

## 3. Open decisions before acceptance

Choose the signed metadata format and threshold model; define monotonic version evidence on platforms without trusted counters; specify storage-provider atomicity; formalize schema migration; define fleet-wave reconciliation; and implement power-loss tests. Until then, RFC-0042 remains Draft.
