# RFC-0043: Capability Rights Algebra

Classification: Normative
Authoritative Source: RFC-0043.md
Requirement-ID: RFC-0043-000
Status: Draft

## 1. Scope

This draft supplies the algebraic work item that blocks capability implementation. It distinguishes semantic authority from the canonical serialized record and from provider-specific live representations.

## 2. Candidate model

Let a capability be `C = (subject-domain, object, type, rights, bounds, epoch, lifetime, delegation-depth, provenance)` and let `valid(C, context, time)` be provider-independent. Rights form a finite partially ordered set `(R, ≤)` where `r1 ≤ r2` means every action allowed by `r1` is allowed by `r2`.

- `RFC-0043.1`: Derivation `derive(C, r, b, t, d)` succeeds only when rights narrow, bounds narrow, lifetime does not expand, delegation depth decreases according to policy, object/type remain compatible, and provenance references the parent.
- `RFC-0043.2`: No operation combines two capabilities to produce rights, bounds, lifetime, or delegation power greater than either authorized parent policy explicitly permits.
- `RFC-0043.3`: Transfer changes the authorized subject/domain according to explicit grant policy; copying bytes or a local handle is not transfer.
- `RFC-0043.4`: Revocation advances or records an epoch/lineage state such that stale live handles fail within a declared bound.
- `RFC-0043.5`: A local capability-space handle has meaning only in its domain and generation. Integer fabrication, reuse after free, and cross-domain copying yield no authority.
- `RFC-0043.6`: Importing a canonical serialized record verifies authenticity, version, provenance, rights, object binding, time/epoch, replay policy, and destination-domain policy before allocating a live handle.
- `RFC-0043.7`: Export is an explicitly authorized derivation/transfer operation, not memory serialization.
- `RFC-0043.8`: CHERI-style packed/tagged address and authority is conformant when untagged or address-only possession grants no authority and monotonic derivation preserves independent semantic bounds and rights.
- `RFC-0043.9`: Denial is fail-closed and has no resource effect except bounded, policy-controlled audit evidence.

## 3. Proof and test obligations

Before acceptance, mechanize the algebra in the selected proof assistant; prove non-amplification, non-forgeability under declared assumptions, transfer conservation, stale-generation rejection, revocation safety, and equivalence of software and native-provider outcomes. Property tests SHALL generate derivation/transfer/revocation histories and differential-test every provider. Cryptographic authenticity does not by itself prove semantic authorization.

## 4. Unresolved choices

The exact right lattice per object type, multi-parent grants, revocation structure, epoch persistence, time semantics, distributed/federated authority, canonical cryptographic format, and recovery-key policy remain open. This draft authorizes prototypes, not production claims.
