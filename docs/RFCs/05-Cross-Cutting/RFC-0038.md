# RFC-0038: Capability Transfer Protocol

Classification: Normative

**Lifecycle note:** Legacy text; treated as Proposed until evidence-gated acceptance.
**Implements invariants:** I-2, I-3.

---

## 1. Scope

This RFC specifies the *capability transfer protocol*: the rules governing how capability tokens move between holders across the Communication Architecture. Transfer builds on the communication-layer capability semantics in `RFC-0027` by defining the full protocol — wire format, validation, failure handling, and revocation integration.

---

## 2. Normative Requirements

### 2.1 Transfer Types

`RFC-0038.1`: The platform supports three transfer types:

| Type       | Sender retains cap? | Description                            |
|------------|--------------------|----------------------------------------|
| `COPY`     | Yes                | Capability copied; sender retains original |
| `MOVE`     | No                 | Capability moved; sender's copy invalidated |
| `DERIVE_COPY` | Yes (narrowed)   | Derived capability with narrower rights created |

### 2.2 Transfer Protocol

`RFC-0038.2`: A capability transfer proceeds as follows:

```
1. Sender verifies it holds the capability with RIGHT_TRANSFER.
2. Sender creates a transfer message:
   - Header: transfer type, rights subset (for DERIVE_COPY)
   - Trailer: the serialized capability_token (RFC-0037), sealed
3. Message is sent via Communication Architecture (RFC-0024 with MSG_CAP_TRANSFER)
4. Receiver's capability subsystem receives the sealed token
5. Receiver verifies:
   a. Seal is valid (RFC-0037.9)
   b. Token is not expired (RFC-0037.14)
   c. Token is not already revoked (RFC-0039)
6. If verification passes:
   - COPY: receiver installs a new token (same rights, receiver's domain)
   - MOVE: sender's token is invalidated; receiver installs the token
   - DERIVE_COPY: receiver installs a new token (narrower rights, derived count incremented)
7. Both sender and receiver emit CapGranted events (RFC-0031)
```

### 2.3 Rights Narrowing During Transfer

`RFC-0038.3`: When transferring with `DERIVE_COPY`, the sender MUST specify a rights subset of the original rights. The resulting token's rights MUST be a proper subset (all requested rights must exist in the original; none may be added).

`RFC-0038.4`: The `rights_derived` counter in the new token MUST be set to `original.rights_derived + 1`.

### 2.4 Domain Scope on Transfer

`RFC-0038.5`: When a capability is transferred to a receiver in a different execution domain (`RFC-0007`), the transferred token's `target_domain_index` is set to the receiver's domain. The capability is bound to the receiver's domain (`CAPF_BOUND` flag set) unless the sender explicitly requests cross-domain transfer with the receiver's permission.

### 2.5 Revocation Integration

`RFC-0038.6`: If the sender's original capability is revoked while a COPY transfer is in-flight, the revocation takes precedence. The receiver's installed capability is also revoked per `RFC-0039`.

`RFC-0038.7`: If the sender's original capability is revoked after a MOVE transfer completes, the transferred token is also revoked per `RFC-0039` (the revocation propagates because the transferred token was derived from the original).

### 2.6 Transfer Failure

`RFC-0038.8`: If transfer fails (seal mismatch, expired, revoked, or communication failure), the sender's original capability is unaffected. The transfer is idempotent — the sender may retry.

---

## 3. Failure Semantics

| Failure                  | Consequence                                               |
|--------------------------|-----------------------------------------------------------|
| No RIGHT_TRANSFER         | Transfer rejected; `ENOCAP` to sender                    |
| Rights not in original    | `DERIVE_COPY` rejected                                    |
| Seal invalid at receiver  | Token not installed; `ECAPSTALE` to receiver              |
| Revocation in-flight       | Both sender and receiver get revoked capabilities        |
| Communication failure      | Transfer aborted; sender retains original                 |
