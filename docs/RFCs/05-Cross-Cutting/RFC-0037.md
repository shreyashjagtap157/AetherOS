# RFC-0037: Capability Token Format

**Status:** Active.
**Implements invariants:** I-1, I-2, I-3, I-13.
**Depends on:** RFC-0007 (Execution Domain), RFC-0013 (Capability Mediation).

---

## 1. Scope

This RFC specifies the canonical binary format of a *capability token*: the unforgeable, opaque, transferable handle that authorizes operations on a resource. The capability token format is the most security-critical data structure in the entire platform — every access control decision ultimately checks a capability token described by this RFC.

This RFC implements I-1, I-2, I-3, and I-13 directly.

---

## 2. Normative Requirements

### 2.1 Capability Token Structure

`RFC-0037.1`: Every capability token has the following fixed structure:

```c
struct capability_token {
    // Identity section (32 bytes)
    uint8_t              type;                 // capability type (see 2.2)
    uint8_t              rights;               // bitmask of granted rights
    uint8_t              flags;               // capability flags (see 2.3)
    uint8_t              reserved1;
    uint32               rights_derived;       // derivation count (for debugging)
    uint64               creation_timestamp_ns; // when created (scheduling time)
    uint64               expires_at_ns;        // 0 = never; absolute scheduling time

    // Reference section (32 bytes)
    struct object_id     target_object;         // RFC-0015: the resource this cap authorizes
    uint32               target_domain_index;   // index into domain table (0 = current domain)
    uint32               reserved2;

    // Integrity section (32 bytes)
    uint8_t              seal[16];             // HMAC-SHA256 of the preceding 64 bytes
    uint8_t              reserved3[16];

    // Total: 96 bytes, 8-byte aligned
};
```

`RFC-0037.2`: Total token size is exactly 96 bytes. No field is variable-length. Any token whose total size is not 96 bytes MUST be rejected as malformed.

### 2.2 Capability Types

`RFC-0037.3`: The following capability types are defined:

| Type  | Name              | Authorized operations                           |
|-------|-------------------|-----------------------------------------------|
| 0     | `CAP_OBJECT`      | Operations on a persistent object              |
| 1     | `CAP_MEMORY`      | Memory region mapping (`RFC-0009`)             |
| 2     | `CAP_ENDPOINT`    | Send/receive on a communication endpoint      |
| 3     | `CAP_DOMAIN`      | Domain creation/management (`RFC-0007`)        |
| 4     | `CAP_CAPABILITY`  | Transfer/revoke other capabilities            |
| 5     | `CAP_STORAGE`    | Storage provider operations                   |
| 6     | `CAP_INTERRUPT`   | Interrupt binding (`RFC-0010`)                 |
| 7     | `CAP_SYNC`        | Synchronization primitives (`RFC-0028`)        |

`RFC-0037.4`: Type-specific semantics: the meaning of the `target_object` field depends on the type. For `CAP_OBJECT`, it is an object identity (`RFC-0015`). For `CAP_MEMORY`, it is a physical address region. For `CAP_ENDPOINT`, it is an endpoint identifier (`RFC-0025`). The type field MUST be checked before interpreting the `target_object`.

### 2.3 Rights Flags

`RFC-0037.5`: The following rights flags are defined. A right is granted (1) or not granted (0):

| Flag position | Right name       | Meaning                                    |
|---------------|------------------|--------------------------------------------|
| 0             | `RIGHT_READ`     | Read access                                |
| 1             | `RIGHT_WRITE`    | Write access                               |
| 2             | `RIGHT_EXECUTE`  | Execute access                              |
| 3             | `RIGHT_MAP`      | Map into address space (`RFC-0009`)         |
| 4             | `RIGHT_TRANSFER` | Transfer to another holder (`RFC-0027`)     |
| 5             | `RIGHT_REVOKE`   | Revoke dependent capabilities (`RFC-0039`)    |
| 6             | `RIGHT_DERIVE`   | Derive a narrower capability               |

`RFC-0037.6`: The `rights` field is an 8-bit bitmask. `RIGHT_TRANSFER`, `RIGHT_REVOKE`, and `RIGHT_DERIVE` are collectively called *meta-rights*. Possessing meta-rights on a capability does not automatically grant any data rights; all must be explicitly granted.

### 2.4 Capability Flags

`RFC-0037.7`: The capability flags field (`flags`) defines token behaviour:

| Flag | Name               | Meaning                                               |
|------|--------------------|-------------------------------------------------------|
| 0x01 | `CAPF_TRANSIENT`    | Not stored in State; lost on domain destroy          |
| 0x02 | `CAPF_REVOCABLE`   | Subject to revocation (`RFC-0039`)                    |
| 0x04 | `CAPF_NAMED`       | Has a stable name (for lookup)                        |
| 0x08 | `CAPF_BOUND`       | Bound to a specific domain; not transferable          |
| 0x10 | `CAPF_SEALED`      | Seal is HMAC; cannot be inspected without key        |

### 2.5 Seal (Integrity)

`RFC-0037.8`: The `seal` field is an HMAC-SHA256 (16 bytes; truncated from the full 32-byte output) computed over the first 64 bytes of the token using the platform's master seal key (derived from the hardware root of trust at bootstrap). Any modification to the first 64 bytes invalidates the seal.

`RFC-0037.9`: The seal MUST be verified before any rights are enforced. A token with an invalid seal MUST be treated as non-existent. The capability subsystem does not distinguish between "no capability" and "invalid capability" — both result in `ECAPSTALE` (`RFC-0025.8`) returned to the accessor.

### 2.6 Address–Authority Separation (I-13)

`RFC-0037.10`: The `target_object` field is an *address* (a name or identifier). The rights in the `rights` field are the *authority*. These are stored in the same token but represent orthogonal concepts (I-13). The seal does not distinguish between address and authority — it seals the entire 64-byte identity block.

`RFC-0037.11`: Implementations that combine address and authority bits into a single bitfield within the seal area are non-conformant. The seal verifies the entire token; the address and authority semantics remain distinct.

### 2.7 Capability Derivation

`RFC-0037.12`: A capability with `RIGHT_DERIVE` may be used to create a new capability with a subset of the original rights (rights narrowing). The new capability's `rights_derived` counter is incremented from the original. The `creation_timestamp_ns` and `target_object` are inherited from the original.

`RFC-0037.13`: Capability derivation does NOT change the identity of the target. The derived capability authorizes the same target as the original, with narrower rights.

### 2.8 Expiration

`RFC-0037.14`: If `expires_at_ns` is non-zero and the current scheduling time exceeds it, the capability MUST be treated as invalid. Expired capabilities cannot be transferred, derived, or used for any operation.

### 2.9 Domain Binding

`RFC-0037.15`: If `CAPF_BOUND` is set, the capability is valid only within the domain identified by `target_domain_index`. A capability bound to domain A presented in domain B is invalid. This is enforced by the Capability Mediation subsystem (`RFC-0013`).

## 3. Failure Semantics

| Failure                  | Consequence                                               |
|--------------------------|-----------------------------------------------------------|
| Token size != 96 bytes   | `ECAPSTALE`; token rejected as malformed                   |
| Seal mismatch            | `ECAPSTALE`; token rejected as tampered                    |
| Type unknown             | `ECAPSTALE`; token rejected as malformed                   |
| Rights not granted       | `ECAPSTALE`; access denied                                 |
| Domain mismatch          | `ECAPSTALE`; cross-domain access denied                    |
| Expired                  | `ECAPSTALE`; expired capability                            |
| Revoked (RFC-0039)       | `ECAPSTALE`; revoked capability                            |

## 4. Conformance Tests

- `CTS-CAP-TOK-1`: validates RFC-0037.2 — exact 96-byte size.
- `CTS-CAP-TOK-2`: validates RFC-0037.4 — type-dependent target interpretation.
- `CTS-CAP-TOK-3`: validates RFC-0037.5 — rights bitmask semantics.
- `CTS-CAP-TOK-4`: validates RFC-0037.6 — meta-rights independence.
- `CTS-CAP-TOK-5`: validates RFC-0037.9 — seal verification before rights check.
- `CTS-CAP-TOK-6`: validates RFC-0037.10 — address/authority orthogonality (seal covers both but they remain distinct).
- `CTS-CAP-TOK-7`: validates RFC-0037.12 — derivation produces narrower rights.
- `CTS-CAP-TOK-8`: validates RFC-0037.14 — expiration enforcement.
- `CTS-CAP-TOK-9`: validates RFC-0037.15 — domain binding enforcement.

## 5. Verification Expectations

Capability token format and enforcement are Tier A. The seal algorithm is Tier A with hardware attestation.
