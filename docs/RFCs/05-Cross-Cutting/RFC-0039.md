# RFC-0039: Capability Revocation Protocol

**Status:** Active.
**Implements invariants:** I-2, I-3.
**Depends on:** RFC-0037 (Capability Token Format), RFC-0038 (Capability Transfer Protocol).

---

## 1. Scope

This RFC specifies the *capability revocation protocol*: how held capability tokens are invalidated, how revocation propagates to derived and transferred tokens, and how revocation is notified to affected holders. Revocation implements I-2 (no ambient authority) by providing the mechanism through which previously granted authority can be withdrawn.

---

## 2. Normative Requirements

### 2.1 Revocation Trigger

`RFC-0039.1`: Revocation may be triggered by:
- Explicit revocation: a holder with `RIGHT_REVOKE` on a capability revokes it.
- Expiration: a capability with a non-zero `expires_at_ns` that has passed is automatically revoked.
- Policy: a declarative revocation policy (e.g., "revoke all capabilities granted by component X") triggers automatic revocation.
- Compulsory: a security policy or legal requirement that mandates revocation of a class of capabilities.

### 2.2 Revocable Capabilities

`RFC-0039.2`: A capability with the `CAPF_REVOCABLE` flag set (`RFC-0037.7`) is subject to revocation. A capability without this flag is non-revocable. A holder MUST NOT attempt to revoke a non-revocable capability; doing so returns `EPERM`.

### 2.3 Revocation Propagation

`RFC-0039.3`: When a capability C is revoked, all capabilities derived from C (via `DERIVE_COPY`, `RFC-0038.1`) are also revoked. This propagation is transitive: if D was derived from C, and E was derived from D, then revoking C also revokes D and E.

`RFC-0039.4`: When a capability C is revoked, all capabilities transferred COPY from C (i.e., copies held by other components) are also revoked. The revocation propagates because the recipient's capability is derived from C's lineage.

`RFC-0039.5`: The revocation graph is maintained by the State Architecture as a Merkle-linked structure (`RFC-0017`). Each capability references its parent capability via `rights_derived` counter and origin. The revocation state is stored as a revocation list: a persistent object (`RFC-0015`) that is part of the system state.

### 2.4 Revocation List

`RFC-0039.6`: The revocation list is a persistent, append-only Merkle tree (separate from the object integrity tree) that records each revocation event:

```c
struct revocation_entry {
    struct object_id     revoked_cap_id;       // hash of the revoked capability
    uint64               revocation_timestamp_ns;
    uint8                revocation_reason;      // 0=explicit, 1=expired, 2=policy, 3=compulsory
    struct object_id     derived_from;         // parent capability if derived
    uint32               derived_chain_length; // number of derivations in chain
};
```

`RFC-0039.7`: The revocation list is integrity-protected and auditable (`RFC-0034`). Each entry is a State object.

### 2.5 Revocation Notification

`RFC-0039.8`: When a capability is revoked, all known holders of that capability (and its transitive dependents) MUST be notified. Notification is delivered as a capability revocation event (`CapRevoked` per `RFC-0031`) to each holder's registered notification endpoint.

`RFC-0039.9`: The platform MUST provide a revocation status query: a component that receives `ECAPSTALE` can query whether the capability was explicitly revoked and if so, when. This is answered by consulting the revocation list.

### 2.6 Revocation vs. Transfer

`RFC-0039.10`: When a capability is transferred (COPY or MOVE, `RFC-0038`), the new holder's copy is recorded in the capability lineage. If the original is later revoked, the copy is also revoked. Transfer does not break revocation chains.

### 2.7 Revocation Performance

`RFC-0039.11`: Revocation MUST complete (including propagation to all known dependents) within a declared bound. The bound MUST be declared in the conformance declaration and MUST be verifiable by CTS. A revocation that is still propagating after the bound is a conformance violation.

## 3. Revocation Algorithm

```
REVOKE(cap C):
1. Verify C has CAPF_REVOCABLE flag; if not, return EPERM.
2. Create revocation_entry E.
3. Append E to revocation list (new Merkle root).
4. For each dependent D in derivation_graph[C]:
     REVOKE(D)
5. For each transferred copy T in transfer_graph[C]:
     REVOKE(T)
6. Emit CapRevoked to all known holders.
7. Return OK.
```

The derivation_graph and transfer_graph are maintained incrementally as transfers and derivations occur.

---

## 4. Failure Semantics

| Failure                  | Consequence                                                 |
|--------------------------|-------------------------------------------------------------|
| Revoke non-revocable      | `EPERM`; no state change                                    |
| Revocation in progress   | Subsequent revocation of same cap queued; no race           |
| Dependent holder not reachable | Notification deferred; revocation still effective  |
| Revocation bound exceeded | Non-conformant per RFC-0039.11                            |
