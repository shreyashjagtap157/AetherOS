# RFC-0040: Verification Tier Methodology

**Status:** Active.
**Implements invariants:** I-7 (forward extensibility), I-8 (verifiable core).
**Depends on:** `Platform-Architecture-Specification-v1.1.md` Section 6 (Verification Tiers).

---

## 1. Scope

This RFC specifies the *methodology* through which components achieve the verification tiers declared in `Platform-Architecture-Specification-v1.1.md` Section 6. It defines what evidence is required for each tier, how that evidence is produced, maintained, and audited, and how the proof cost (person-years, re-verification effort) is estimated and managed.

This RFC is process-level, not product-level: it governs how verification is done, not what is verified.

---

## 2. Normative Requirements

### 2.1 Tier A — Machine-Verified

`RFC-0040.1`: To claim Tier A, a component MUST produce:
1. A machine-readable formal specification (in a declared formal language, e.g., ACSL, Refinement Calculus, Why3, or K-framework) stating all functional invariants.
2. A machine-checked proof (using a declared prover, e.g., Coq, Isabelle/HOL, Why3, Verus) establishing that the implementation satisfies the specification.
3. A declared proof-fragility class: how much surface change (measured in changed lines of specification + changed lines of code) triggers re-proof.
4. A proof-maintenance budget estimate: person-years per year of platform lifetime.

`RFC-0040.2`: The specification language and prover used MUST be declared in the conformance declaration. The specification MUST be in version control and MUST be part of the implementation artifact.

`RFC-0040.3`: The proof artifacts MUST be independently reproducible: running the prover on the specification with the declared prover version MUST reproduce the proof without additional human intervention.

`RFC-0040.4`: Proof-fragility class is one of:
- **Class PF-1 (Minimal):** Re-proof required only for direct spec changes; implementation changes that don't affect spec don't require re-proof.
- **Class PF-2 (Moderate):** Re-proof required for spec changes and implementation changes that affect declared invariants.
- **Class PF-3 (Conservative):** Re-proof required for any change to the component.

`RFC-0040.5`: The declared proof-fragility class MUST be consistent with the proof structure. A claim of PF-1 without modular proofs (where spec changes and implementation changes are isolated) is non-conformant.

### 2.2 Tier B — Model-Checked

`RFC-0040.6`: To claim Tier B, a component MUST produce:
1. A finite-state model of the component in a declared model-checking language (e.g., Promela/SPIN, TLA+, Alloy, nuXmv).
2. A property specification (in LTL, CTL, or declared equivalent) for all invariants.
3. A verification report from the declared model-checker showing that all properties are satisfied.
4. A model-fragility class analogue to proof-fragility for Tier A.

`RFC-0040.7`: The state-space of the model MUST be finite. If the component's natural state space is infinite, abstraction is required, and the abstraction must be declared and justified.

### 2.3 Tier C — Property-Tested

`RFC-0040.8`: To claim Tier C, a component MUST produce:
1. A declared property set (in a machine-readable format).
2. A generative test harness (e.g., using a fuzzing framework such as AFL, libFuzzer, or QuickCheck).
3. A declared seed and time budget for reproducibility.
4. A coverage report (branch coverage minimum declared; coverage below minimum is non-conformant).

`RFC-0040.9`: The generative tests MUST be run as part of the CI pipeline, and failures MUST block integration.

### 2.4 Tier D — Conventional Testing

`RFC-0040.10`: To claim Tier D, a component MUST pass the declared test suite (unit, integration, regression) with at least 80% statement coverage. Coverage below 80% requires documented justification in the conformance declaration.

### 2.5 Verification Maintenance

`RFC-0040.11`: Every Tier A and Tier B claim MUST be re-evaluated at each platform release. The re-evaluation report MUST be published as part of the conformance declaration. A proof that passes verification once but is not maintained is non-conformant for Tier A/B.

`RFC-0040.12`: When a component changes in a way that requires re-verification, the verification team (or the component author with verification expertise) MUST re-run the verification and update the artifact. The cost of this re-verification effort is part of the verification budget estimated in RFC-0040.1.

### 2.6 Economic Cost Tracking

`RFC-0040.13`: Every implementation claiming Tier A MUST include in its conformance declaration:
- The initial proof investment (person-years to first proof).
- The per-release re-proof cost (person-years per platform release).
- The proof-fragility class.
- The estimated total verification cost over a 10-year window.

This data is used by the Critical-Path Admission Test (`Platform-Architecture-Specification-v1.1.md` Section 3.3) to evaluate whether kernel residency is justified by the verification cost.

### 2.7 Verification Tiers and Platform Invariants

`RFC-0040.14`: For any invariant declared in `Platform-Architecture-Specification-v1.1.md` Section 2 (I-1 through I-13), the implementation MUST declare which verification tier is claimed for each component that realizes that invariant. If no component claims Tier A for a given invariant, the implementation MUST document why the invariant is still satisfied.

## 3. Verification Tool Registry

`RFC-0040.15`: The platform maintains a declared list of acceptable specification languages, provers, model-checkers, and test harnesses. A tool not on this list may be used if it is formally documented to be equivalent to a listed tool. The registry is maintained as a separate RFC (not this one).

The initial registry includes: Coq, Isabelle/HOL, Why3, Verus, TLA+, Promela/SPIN, nuXmv, Alloy, ACSL.

---

## 4. Failure Semantics

| Failure                  | Consequence                                                     |
|--------------------------|------------------------------------------------------------------|
| Proof not reproducible    | Tier A claim invalidated; component downgraded to Tier B           |
| Coverage below 80% (Tier D) | Tier D claim invalidated without documented justification    |
| Maintenance not performed | Tier A/B claim invalidated for next release                     |
| Economic cost not declared | Tier A claim invalidated; Critical-Path admission test fails  |

---

## 5. Conformance Tests

- `CTS-VERIF-1`: validates RFC-0040.1 — proof artifacts exist and are machine-readable.
- `CTS-VERIF-2`: validates RFC-0040.3 — proof reproducible with declared tool version.
- `CTS-VERIF-3`: validates RFC-0040.5 — proof-fragility class consistent with proof structure.
- `CTS-VERIF-4`: validates RFC-0040.11 — re-evaluation at each platform release.
- `CTS-VERIF-5`: validates RFC-0040.13 — economic cost declared for Tier A.
