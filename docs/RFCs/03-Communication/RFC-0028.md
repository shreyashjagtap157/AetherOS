# RFC-0028: Synchronization

**Status:** Active.
**Implements invariants:** I-10 (explicit failure semantics).
**Depends on:** RFC-0024 (Message Format), RFC-0025 (Endpoint Model).

---

## 1. Scope

This RFC specifies synchronization primitives for inter-thread and inter-component coordination. Synchronization is the mechanism that prevents race conditions, enforces ordering, and implements blocking semantics in the platform.

This RFC does not specify distributed synchronization (which requires the v2 federation protocol).

---

## 2. Normative Requirements

### 2.1 Primitive Set

`RFC-0028.1`: The platform MUST provide the following synchronization primitives:
- **Mutex** — binary lock; supports ownership, contention queue, priority inheritance
- **Semaphore** — counting lock with non-negative count; supports acquire/release
- **Condition variable** — wait/notify pair; requires a mutex to wait on
- **Event** — single-use or auto-reset notification; supports broadcasting
- **Futex** — lightweight lock for intra-domain fast-path synchronization (userspace when uncontended)

### 2.2 Mutex

`RFC-0028.2`: A mutex has states: `UNLOCKED`, `LOCKED_UNCONTENDED`, `LOCKED_CONTENDED`. Transitions MUST be atomic.

`RFC-0028.3`: The platform MUST support priority inheritance on mutexes. When a higher-priority thread is blocked on a mutex held by a lower-priority thread, the holder's priority MUST be temporarily elevated to that of the blocked thread. The elevation MUST be undone when the mutex is released.

`RFC-0028.4`: Priority inheritance chains MUST be documented if depth exceeds 3. Unbounded priority-inheritance chains are a Safety-Critical profile violation.

### 2.3 Semaphore

`RFC-0028.5`: Semaphore `acquire()` MUST block until the count is positive, then atomically decrement it and return. `release()` atomically increments the count and wakes one waiting acquirer.

### 2.4 Condition Variables

`RFC-0028.6`: A condition variable `wait()` atomically releases the associated mutex and blocks the thread. On wake, `wait()` re-acquires the mutex before returning.

`RFC-0028.7`: `notify_one()` wakes one waiter. `notify_all()` wakes all waiters. Which waiters are woken first is unspecified (implementation decides); but all MUST eventually be woken.

### 2.5 Deadlock Avoidance

`RFC-0028.8`: The platform SHOULD enforce a lock-ordering hierarchy for mutexes: if mutex A must be acquired before mutex B, the hierarchy is declared in the component manifest and the platform MUST verify at runtime that no thread acquires them in the reverse order. Lock-order violations MUST emit `LockOrderViolation` per `RFC-0031.51`.

`RFC-0028.9`: The platform MUST provide a deadlock detection mode (enabled per profile) that identifies cycles in the wait-for graph and breaks them by revoking the most recently acquired lock in the cycle. This is a Safety-Critical profile requirement.

### 2.6 Timeout

`RFC-0028.10`: All blocking primitives MUST support an absolute timeout parameter (`RFC-0012` time). If the timeout expires before the primitive is satisfied, the primitive returns a timeout error without modifying the synchronisation state. Timeouts MUST NOT cause state corruption.

### 2.7 Scheduler Integration

`RFC-0028.11`: When a thread blocks on a synchronization primitive, the scheduler (`RFC-0011`) is notified and the thread is placed in `BLOCKED` state. When the primitive is signaled, the scheduler is notified and the blocked thread is requeued to `READY`.

## 3. Data Structures

```c
enum sync_primitive_type {
    MUTEX         = 0,
    SEMAPHORE     = 1,
    CONDITION_VAR = 2,
    EVENT         = 3,
    FUTEX         = 4,
};

struct mutex_descriptor {
    uint8                   state;          // UNLOCKED, LOCKED_UNCONTENDED, LOCKED_CONTENDED
    struct thread_id        owner;          // valid only when LOCKED_*
    uint32                  waiters;        // count of waiting threads
    struct priority_boost   boost;          // active priority inheritance state
};

struct lock_order_declaration {
    struct mutex_descriptor *first;
    struct mutex_descriptor *second;        // first must be acquired before second
};
```

## 4. Failure Semantics

| Failure                  | Consequence                                               |
|--------------------------|-----------------------------------------------------------|
| Double lock (same thread)| `EDEADLK`; second lock rejected                          |
| Unlock without owning     | `EPERM`; rejection per RFC-0031.52                        |
| Lock-order violation      | `LockOrderViolation` event; optional deadlock detection   |
| Timeout during acquire    | `ETIMEDOUT`; state unchanged                              |
