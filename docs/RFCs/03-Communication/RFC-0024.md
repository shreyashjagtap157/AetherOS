# RFC-0024: Message Format

Classification: Normative
Authoritative Source: RFC-0024.md
Requirement-ID: RFC-0024-000
Status: Proposed

**Lifecycle note:** Legacy text; treated as Proposed until evidence-gated acceptance.
**Implements invariants:** I-10 (explicit failure semantics).
**Depends on:** RFC-0007 (Execution Domain), RFC-0037 (Capability Token Format).

---

## 1. Scope

This RFC specifies the canonical binary message format for all inter-component and inter-domain communication in the platform. Every message — whether a synchronous IPC call, an asynchronous event, a capability transfer, or a stream chunk — uses this format as its wire representation.

This RFC does not specify routing (`RFC-0026`) or transport guarantees.

---

## 2. Normative Requirements

### 2.1 Message Structure

`RFC-0024.1`: Every message has the following fixed header followed by a variable payload:

```c
struct message_header {
    uint32              magic;            // 0x434F4D50 ("COMP") — platform signature
    uint16              version;          // Format version; this RFC defines version 1
    uint16              header_len;       // Length of this header in bytes
    uint64              message_id;       // Globally unique per-source sequence number
    struct endpoint_id  src_endpoint;     // Source endpoint (RFC-0025)
    struct endpoint_id  dst_endpoint;     // Destination endpoint (RFC-0025)
    uint32              payload_len;      // Length of payload in bytes
    uint32              trailer_len;      // Length of trailer in bytes
    uint8               flags;            // Message flags (see below)
    uint8               urgency;          // 0 = lowest, 255 = highest
    uint16              reserved;
    uint8               capability_count; // Number of capability tokens in trailer
    // header_len bytes total; followed by payload_len bytes, followed by trailer_len bytes
};
```

### 2.2 Flags

`RFC-0024.2`: The following flags are defined:

| Flag              | Value | Meaning                                           |
|-------------------|-------|---------------------------------------------------|
| `MSG_FAST`        | 0x01  | Fast path; skip logging if possible              |
| `MSG_CAP_TRANSFER`| 0x02  | Trailer contains capability tokens               |
| `MSG_STREAM`      | 0x04  | Partial message; more chunks follow              |
| `MSG_NO_REPLY`    | 0x08  | Sender does not expect a reply                   |
| `MSG_ERROR`       | 0x10  | This message is an error response                 |

### 2.3 Trailer

`RFC-0024.3`: The trailer, when present (trailer_len > 0), contains:
- Zero or more capability tokens (count = capability_count)
- Optional inline error data (when `MSG_ERROR` flag is set)

`RFC-0024.4`: Capability tokens in the trailer are serialized per `RFC-0037`. The count is in the header. The receiver validates each token's rights before using it.

### 2.4 Payload

`RFC-0024.5`: The payload is opaque to the Communication Architecture. Its interpretation is a contract between sender and receiver. The payload MUST NOT be interpreted by the Communication layer except for size validation.

`RFC-0024.6`: Maximum message size is declared by each endpoint at registration (`RFC-0025`). Messages exceeding the endpoint's declared maximum MUST be rejected with `EMSGSIZE`.

### 2.5 Error Responses

`RFC-0024.7`: Error responses use the same message format with the `MSG_ERROR` flag set and the error code in the first 4 bytes of the payload. Error codes are defined in `RFC-0025.8`.

### 2.6 Byte Order

`RFC-0024.8`: All multi-byte fields in the header use network byte order (big-endian). Implementations on little-endian platforms MUST convert on send/receive.

## 3. Message Sequences

### 3.1 Request–Reply (Synchronous)

```
Sender → [MSG_NO_REPLY not set] → Receiver
Receiver → [MSG_ERROR or response] → Sender
```

`RFC-0024.9`: A reply message MUST have the same `message_id` as the request it answers, with `src_endpoint` and `dst_endpoint` swapped.

### 3.2 One-Way (Asynchronous)

```
Sender → [MSG_NO_REPLY set] → Receiver
(no reply expected)
```

### 3.3 Stream

```
Sender → [MSG_STREAM set; chunk 1] → Receiver
Sender → [MSG_STREAM set; chunk 2] → Receiver
...
Sender → [MSG_STREAM not set; final chunk] → Receiver
```

`RFC-0024.10`: Stream chunks share the same `message_id` with an incrementing chunk counter in the trailer. The receiver reassembles in order. Out-of-order chunks MUST be reported per `RFC-0031.47`.

## 4. Failure Semantics

| Failure                  | Consequence                                               |
|--------------------------|-----------------------------------------------------------|
| Magic mismatch           | Message discarded; `ProtocolError` per RFC-0031.48        |
| Version mismatch          | Message rejected; `VersionMismatch` per RFC-0031.49       |
| Payload exceeds max       | `EMSGSIZE`; message rejected                              |
| No such destination       | `ENODEST`; error response per RFC-0024.7                  |
| Out-of-order stream chunk | Event per RFC-0031.47; stream reassembly failure           |
