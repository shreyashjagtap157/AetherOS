# RFC-0029: Streaming

**Status:** Active.
**Implements invariants:** I-10.
**Depends on:** RFC-0024 (Message Format), RFC-0025 (Endpoint Model), RFC-0026 (Routing).

---

## 1. Scope

This RFC specifies *streaming communication*: the mechanism for sending large data that exceeds a single message's maximum size, or for delivering data progressively before the complete content is available.

Stream communication is not a separate mechanism from the message format; it uses the `MSG_STREAM` flag in `RFC-0024` to indicate partial delivery.

---

## 2. Normative Requirements

### 2.1 Stream Establishment

`RFC-0029.1`: A stream is established by sending a message with the `MSG_STREAM` flag set and a non-zero `stream_id` in the trailer. The `stream_id` is a client-selected identifier that groups stream chunks. The destination endpoint's reception of this message constitutes acceptance of the stream.

`RFC-0029.2`: A sender MUST declare the total expected size (if known) in the first chunk's trailer, or indicate `size_unknown`. The declaration is advisory; the platform does not enforce it.

### 2.2 Chunk Ordering

`RFC-0029.3`: Stream chunks are delivered in order. The receiver MUST reassemble them in the order they were sent. Out-of-order chunks MUST be reported as `StreamOutOfOrder` per `RFC-0031.53`.

`RFC-0029.4`: A stream is complete when a message is received without the `MSG_STREAM` flag set (the final chunk). If the final chunk is not received within a declared timeout (from the first chunk), the stream is considered abandoned and the receiver MAY discard partial content.

### 2.3 Flow Control

`RFC-0029.5`: The receiver MUST declare a receive window: the maximum total bytes it will buffer before signalling backpressure. The sender MUST respect this window and pause sending if it receives a `STREAM_BACKPRESSURE` control message.

`RFC-0029.6`: The Communication Architecture SHOULD implement receive-window-based flow control. If not implemented, the sender's pace is unconstrained, and the platform is non-conformant for the Cloud and HPC profiles.

### 2.4 Stream Cancellation

`RFC-0029.7`: Either endpoint MAY cancel a stream by sending a message with `MSG_STREAM_CANCEL` flag set. On receiving a cancel, the receiver discards all previously received chunks and emits `StreamCancelled` per `RFC-0031.54`.

### 2.5 Multiplexing

`RFC-0029.8`: Multiple streams MAY be multiplexed over a single endpoint connection, distinguished by their `stream_id`. The platform MUST support at least 256 simultaneous streams per endpoint.

## 3. Data Structures

```c
struct stream_header {          // trailer content for first and subsequent chunks
    uint64       stream_id;      // client-assigned; unique per sender
    uint64       chunk_index;    // 0-based index; monotonically increasing
    uint64       total_size;     // 0 if unknown
    uint64       chunk_size;     // bytes in this chunk
};

struct stream_backpressure {
    uint64       stream_id;
    uint8        pause;          // 1 = pause, 0 = resume
};
```

---

## 4. Failure Semantics

| Failure                  | Consequence                                                 |
|--------------------------|-------------------------------------------------------------|
| Out-of-order chunk        | `StreamOutOfOrder` per RFC-0029.3                          |
| Abandoned stream          | Partial content discarded; event per RFC-0031.55             |
| Receive window exceeded   | Platform sends `STREAM_BACKPRESSURE`; sender pauses         |
| Cancel received          | `StreamCancelled`; partial content discarded                 |
