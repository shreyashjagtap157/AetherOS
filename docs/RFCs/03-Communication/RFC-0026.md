# RFC-0026: Routing

**Status:** Active.
**Implements invariants:** I-1 (authority mediation).
**Depends on:** RFC-0024 (Message Format), RFC-0025 (Endpoint Model), RFC-0037 (Capability Token Format).

---

## 1. Scope

This RFC specifies the routing subsystem: how messages are delivered from a source endpoint to a destination endpoint within and across execution domains. Routing is responsible for finding the path, enforcing capability rights, and handling delivery failures.

This RFC does not specify the transport layer (which physical network or shared-memory mechanism is used); that is the concern of the provider abstraction.

---

## 2. Normative Requirements

### 2.1 Route Resolution

`RFC-0026.1`: Routing resolves a `(src_endpoint, dst_endpoint)` pair to a sequence of one or more hops. Each hop contains:
- The next routing node (or final destination)
- The capability required to traverse that hop
- The transport to use for that hop

`RFC-0026.2`: Route resolution is performed by the routing subsystem using a routing table that maps destination patterns to next hops. The routing table is populated by the Composition Architecture (`RFC-0003`) and by explicit routing policy declarations.

### 2.2 Capability-Based Routing

`RFC-0026.3`: Every hop requires a capability token authorizing traversal. The routing table entry associates each next hop with a required capability class. A sender that lacks the required capability for a hop MUST be rejected with `ENOCAP`.

`RFC-0026.4`: Routing tables MUST be consistent with the capability graph: a route MUST NOT exist if the sender lacks the required capability chain. Violations are non-conformant.

### 2.3 Intra-Domain Routing

`RFC-0026.5`: Within a single execution domain, routing is a single hop. The routing table entry is the destination endpoint itself. The required capability is `SEND` on the destination endpoint (`RFC-0025.5`).

### 2.4 Inter-Domain Routing

`RFC-0026.6`: Across execution domains, routing is two or more hops. The route crosses domain boundaries at documented boundary nodes. Each boundary crossing requires a cross-domain capability per `RFC-0013`.

`RFC-0026.7`: **v1 restriction:** Multi-domain routing is explicitly restricted to single-execution-domain deployments. Implementations claiming multi-domain routing in v1 are non-conformant. Multi-domain routing is a v2 feature.

### 2.5 Failure Handling

`RFC-0026.8`: If a message cannot be routed (no route exists, capability missing, destination unreachable), the routing subsystem MUST return an error to the sender with `ENODEST` or `ENOCAP` and MUST NOT silently drop the message.

`RFC-0026.9`: If a delivery attempt fails after routing succeeds (e.g., destination endpoint queue full), the routing subsystem MAY retry with exponential backoff, up to a declared maximum retries. After maximum retries, the sender receives `EQUOTA` and the message is dropped.

### 2.6 Routing Table Consistency

`RFC-0026.10`: The routing table MUST be consistent with the current set of registered endpoints and current capability graph. When an endpoint is deregistered (`RFC-0025.10`), all routing table entries referring to it MUST be invalidated. Routers that continue directing messages to a deregistered endpoint are non-conformant.

## 3. Data Structures

```c
struct route_hop {
    struct endpoint_id    next_hop;          // intermediate or final destination
    uint8                 required_cap_class; // minimum capability class for this hop
    uint8                 transport;        // provider-specific transport ID
    uint32                weight;           // for equal-cost multi-path
};

struct route_entry {
    struct endpoint_id    destination;        // pattern or exact match
    uint32                hop_count;
    struct route_hop      hops[];            // ordered array of hops
};

struct routing_table {
    uint32                 entry_count;
    struct route_entry     entries[];
};
```

---

## 4. Routing Algorithm

`RFC-0026.11`: Route resolution MUST complete in O(log N) or better where N is the number of routing table entries. N is bounded by the number of registered endpoints.

`RFC-0026.12`: Routing decisions MUST be deterministic given identical routing table state and identical endpoints. Non-deterministic routing is non-conformant.

---

## 5. Failure Semantics

| Failure                  | Consequence                                             |
|--------------------------|---------------------------------------------------------|
| No route to destination   | `ENODEST` to sender                                     |
| Capability missing for hop | `ENOCAP` to sender                                    |
| Destination queue full    | Retry with backoff; then `EQUOTA`                      |
| Endpoint deregistered     | Routing table entry invalidated; `ENODEST` to sender     |
