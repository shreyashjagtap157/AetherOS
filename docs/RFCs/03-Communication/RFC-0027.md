# RFC-0027: Capability Transfer

**Status:** Active.
**Implements invariants:** I-2 (no ambient authority), I-3 (least privilege).
**Depends on:** RFC-0024 (Message Format), RFC-0025 (Endpoint Model), RFC-0037 (Capability Token Format), RFC-0038 (Capability Transfer Protocol).

---

## 1. Scope

This RFC specifies how capability tokens are transferred between components through the Communication Architecture. Capability transfer is the primary mechanism by which authority propagates across components, and is the architectural implementation of I-2 (no ambient authority).

This RFC is about *communication-layer* capability transfer: the wire format, endpoint semantics, and delivery guarantees for capability tokens in messages.

---

## 2. Normative Requirements

### 2.1 Transfer Semantics

`RFC-0027.1`: Capability tokens are transferred by including them in the message trailer (`RFC-0024.3`). The `MSG_CAP_TRANSFER` flag in the message header (`RFC-0024.2`) indicates that the trailer contains capability tokens.

`RFC-0027.2`: A capability token transferred in a message is a *copy*. The sender retains its own capability token after transfer. Capability transfer is a duplication operation, not a move operation, unless the sender explicitly transfers with revocation (`RFC-0039`).

`RFC-0027.3`: A component that receives a capability token in a message acquires the rights declared in the token. The receiver's domain scope for that token is the receiver's domain.

### 2.2 Rights Narrowing

`RFC-0027.4`: When a component transfers a capability token it holds to another component, it MAY narrow the rights. It MUST NOT widen them. The transferred token's rights are a subset of the original token's rights. Rights widening is a capability fault per `RFC-0013`.

### 2.3 Authorization

`RFC-0027.5`: A component MAY only send a capability token in a message if the component holds a capability that includes `TRANSFER` rights for that token. The communication layer verifies this before accepting the message for sending.

`RFC-0027.6`: The Communication Architecture does not interpret capability token contents. It only verifies that the sender holds the required `TRANSFER` right. The meaning of the capability is a matter for `RFC-0037` and `RFC-0038`.

### 2.4 Capability Integrity in Transit

`RFC-0027.7`: Capability tokens in transit MUST be integrity-protected (either by the message's integrity system or by a separate integrity mechanism in the capability transfer protocol). A corrupted capability token in transit MUST be detected and rejected; the message MUST NOT be delivered.

`RFC-0027.8`: Capability tokens in a message trailer are part of the message's integrity verification (`RFC-0024`). If the message integrity check fails, all capability tokens in the trailer are invalid.

### 2.5 Revocation Propagation

`RFC-0027.9`: If a capability token is revoked (`RFC-0039`) after it has been transferred, the revocation propagates to all known holders. A holder that attempts to use a revoked capability receives `ECAPSTALE` per `RFC-0025.8`. The Communication Architecture MUST support capability revocation notifications delivered as messages to affected endpoints.

---

## 3. Transfer Protocol Sequence

```
1. Sender holds capability C with TRANSFER right.
2. Sender calls SEND with C in trailer, MSG_CAP_TRANSFER flag set.
3. Communication layer verifies sender holds C + TRANSFER.
4. Communication layer includes C (possibly narrowed) in message trailer.
5. Message is routed (RFC-0026) and delivered to destination.
6. Receiver's communication layer extracts C from trailer.
7. Receiver's capability system installs C with the receiver's domain scope.
```

---

## 4. Failure Semantics

| Failure                  | Consequence                                               |
|--------------------------|-----------------------------------------------------------|
| No TRANSFER right         | `ENOCAP`; message not sent                                 |
| Rights widening attempted | Capability fault; message not sent                         |
| Token corrupted in transit | Message integrity check fails; message rejected           |
| Revocation mid-transit    | Token invalidated before delivery; ECAPSTALE on use       |
